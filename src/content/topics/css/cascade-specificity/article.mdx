# 层叠、优先级与继承

## 一句话结论

样式最终取哪个值由层叠算法逐级筛选：来源与重要性 → 层叠层 → 作用域接近度 → 优先级 → 出现顺序；优先级只是其中一环，用 `@layer` 和 `:where()` 组织样式，比堆类名或 `!important` 更可控。

## 前置知识

请先阅读[语义化 HTML 与可访问性](/topics/semantic-accessibility)，了解结构与选择器的关系。本文默认读者会写基本选择器，知道伪类与伪元素的区别，并接触过至少一次"样式明明写了却没生效"的排查。

## 核心机制

### 层叠是一条流水线

对每个元素的每个属性，浏览器收集所有命中的声明，然后按固定顺序淘汰：

1. **来源与重要性**。普通声明的顺序是：用户代理样式 → 用户样式 → 作者样式（后者优先）。带 `!important` 的声明单独排一档，且顺序**整体反转**：作者 important 最低，用户 important 更高，用户代理 important 最高。这不是设计怪癖——它保证用户为了可读性设置的强制样式（放大字号、高对比度）不会被网站覆盖掉。过渡与动画各自还有专门位置。
2. **层叠层**。`@layer` 声明的层按声明顺序排列，**后声明的层优先级更高**；未分层的样式优先级高于所有层。带 `!important` 时层顺序同样反转。
3. **作用域接近度**。`@scope` 内的规则，作用域根离目标元素更近的胜出。
4. **优先级**。三元组比较，见下节。
5. **出现顺序**。前面全都相同时，后出现的声明胜出。

排查"样式不生效"时，应当按这个顺序自上而下问，而不是一上来就数类名。

### 优先级只是三个计数

优先级是一个三元组 `(A, B, C)`：

- `A`：ID 选择器的数量。
- `B`：类、属性选择器、伪类的数量。
- `C`：元素类型选择器和伪元素的数量。

从左往右逐位比较，**不进位**：`(0, 11, 0)` 仍然小于 `(1, 0, 0)`，一百个类也压不过一个 ID。

几个容易记错的点：

- 通配符 `*`、组合符 `>`、`+`、`~`、` ` 都不贡献优先级。
- `:not()`、`:is()`、`:has()` 自身不计数，但取**参数中优先级最高的那一个**。
- `:where()` 恒为 `(0, 0, 0)`，无论参数写什么。
- 内联 `style` 属性不参与三元组比较，它排在更高一档；只有 `!important` 能覆盖它。
- 属性选择器和类同级，`[data-state="open"]` 与 `.open` 权重一样。

```css
/* (0,2,1)：两个类 + 一个元素 */
.card.is-active p { color: red; }

/* (0,1,1)：:where 不计权重，等价于 .highlight p 里少一个类 */
:where(.card) .highlight p { color: blue; }

/* (0,1,0)：:is 取参数中最高者，这里全是类 */
:is(.a, .b) { color: green; }

/* (1,0,0)：:not 取参数中最高者 */
:not(#main) { color: gray; }
```

### 用 @layer 代替权重竞赛

层叠层把"谁该覆盖谁"从选择器写法里解放出来：

```css
@layer reset, vendor, components, utilities;

@layer reset {
  /* 用 :where 把重置写成零优先级，任何组件样式都能轻松覆盖 */
  :where(h1, h2, h3, p, ul, ol) { margin-block: 0; }
}

@layer components {
  .button { padding: 8px 16px; background: var(--color-accent); }
}

@layer utilities {
  /* 后声明的层更高，工具类不需要 !important 就能覆盖组件 */
  .mt-0 { margin-top: 0; }
}
```

这样第三方库放进 `vendor` 层，无论它内部写了多少 ID 选择器，都会被后声明的 `components` 层覆盖——因为层的比较发生在优先级之前。

### 继承是另一条规则

继承和层叠是两件事：**只有当某个元素的某个属性没有任何声明命中时**，才会考虑继承。也就是说，一条命中的声明（哪怕优先级很低）也会阻止继承。

可继承的属性主要是文本相关的：`color`、`font-*`、`line-height`、`letter-spacing`、`text-align`、`visibility`、`cursor` 等；盒模型与布局属性（`margin`、`padding`、`border`、`display`、`width`）不可继承。

四个显式关键字负责手动控制：

- `inherit`：强制取父元素的计算值。
- `initial`：取属性的规范初始值（注意 `display` 的初始值是 `inline`，不是"原本的样子"）。
- `unset`：可继承属性等价于 `inherit`，否则等价于 `initial`。
- `revert`：回滚到上一个来源的值——作者样式里写 `revert` 会露出用户代理样式，这才是"恢复浏览器默认外观"的正确写法。

`all: revert` 常用于把一段第三方内容拉回默认外观，比 `all: initial` 安全得多。

## 项目应用

1. 建立层次约定：`@layer reset, base, vendor, components, utilities;` 在入口文件顶部一次声明，后续文件只往层里补内容。
2. 重置和基础排版用 `:where()` 包裹，让它们优先级为零，组件永远能覆盖而不需要提高权重。
3. 组件内部选择器保持扁平，尽量单类；需要变体时用 `data-*` 属性或额外的修饰类，不要靠加深后代层级来提高权重。
4. 禁止在业务代码里用 ID 做样式钩子；ID 留给锚点和 `label for`。
5. `!important` 只保留给两类场景：覆盖无法修改的第三方内联样式，以及 `utilities` 层里明确表示"就是要赢"的极少数原子类。每次使用都写注释说明原因。
6. 排查时打开 DevTools 的 Styles 面板，被划掉的声明会显示覆盖来源；把鼠标移到选择器上可以看到计算出的优先级。

## 边界与反例

"选择器越长越强"不成立：长度不等于优先级，`(0,1,0)` 的单类会输给 `(0,2,0)` 的两个类，但 `(0,3,0)` 与 `(0,3,0)` 相同时比的是顺序而不是长度。

"`!important` 是最高优先级"也不准确。它改变的是**来源排序**，用户样式表里的 `!important` 会盖过作者的 `!important`；而且两条同为作者 `!important` 的声明之间，仍然要继续比层、比优先级、比顺序。

"给父元素设 `border`，子元素会继承"是把继承和视觉包含搞混了：`border` 不可继承，子元素看起来在框内只是布局结果。

`:where()` 让优先级归零很好用，但它也意味着**任何**同层同权重的后续规则都能覆盖它，包括你不希望覆盖的；要保持基础样式稳定时应该用层而不是零权重。

最后，层叠决定的是**属性取值**，和绘制时谁盖住谁无关，后者见[层叠上下文与 z-index](/topics/stacking-context)——名字里都有"层叠"，但两套机制完全独立。

## 面试回答

一个属性最终取哪个值，是层叠算法一步步筛出来的，优先级只是其中一环。顺序是：先比来源与重要性，作者的普通声明高于用户和用户代理，但带 `!important` 时这个顺序整体反转，所以用户的 `!important` 最高，这是无障碍设计的保障；再比层叠层，后声明的层赢，`!important` 时层顺序同样反转；然后是 `@scope` 的作用域接近度；接着才是优先级，按 ID、类与属性与伪类、元素与伪元素三组从左到右比较，不进位，再多的类也压不过一个 ID；最后才是出现顺序。内联样式相当于更高一档来源。

继承是另一回事：只有当元素上没有任何声明命中该属性时才发生，而且只有部分属性可继承。工程上我用 `@layer` 把重置、第三方、组件、工具类分层，基础样式用 `:where()` 写成零优先级，这样覆盖靠层次而不是靠堆权重或 `!important`。

## 深度追问

1. **为什么 `!important` 会让来源顺序反转？** 因为 `!important` 最初的设计目的是让**用户**能强制自己的可访问性偏好。如果作者的 `!important` 能盖过用户的，这个机制就失效了，所以规范规定带 `!important` 时来源顺序整体倒过来。
2. **`:is()` 和 `:where()` 的区别？** 匹配行为完全相同，差别只在优先级：`:is()` 取参数列表中优先级最高的一项，`:where()` 恒为零。想批量书写又不想抬高权重时用 `:where()`。
3. **`unset` 和 `revert` 有什么不同？** `unset` 是"可继承就继承、不可继承就回到规范初始值"，会抹掉用户代理样式；`revert` 是"回滚到上一个来源"，在作者样式里写它会露出浏览器默认样式，更适合"恢复默认外观"的需求。
