# 语义化 HTML 与可访问性

## 一句话结论

可访问性的起点不是“多写 ARIA”，而是让元素的语义、可访问名称、角色、状态、焦点顺序和键盘行为与用户看到的界面一致。优先使用原生 HTML；原生语义不足时再用 ARIA 补充，并亲自实现 ARIA 不会提供的交互行为。

## 前置知识

本专题是 HTML 与可访问性章节的起点，元数据没有站内前置专题。开始前只需要认识元素、属性、DOM 树和 `click`、`keydown` 等基本事件：元素表达文档结构，属性补充状态，DOM 顺序通常决定阅读与键盘导航的基础顺序。后文会从这些通用 HTML 基础建立可访问名称、角色和状态，不要求先掌握 ARIA。

## 核心机制

### 原生语义优先于 ARIA

浏览器会根据 HTML 构建可访问性树，辅助技术从中读取控件是什么、叫什么、当前处于什么状态。`button` 天生具有按钮角色，可以进入顺序焦点，支持 Enter 和 Space 激活，并能响应 `disabled`。`div` 只是通用容器：添加 `role="button"` 只改了暴露给辅助技术的角色，不会自动获得焦点、键盘事件、禁用语义或表单行为。

因此选择顺序应当是：

1. 先找与意图匹配的原生元素，例如导航用 `nav`、标题用 `h1` 至 `h6`、操作用 `button`、跳转用带 `href` 的 `a`、输入用有 `label` 的表单控件。
2. 如果设计的是 HTML 没有直接提供的复合组件，再参考 WAI-ARIA Authoring Practices 确定角色、状态、键盘模型和焦点管理。
3. 把 ARIA 当作语义契约，不当作行为补丁。契约写了什么，代码和视觉表现就必须同步什么。

“No ARIA is better than bad ARIA”并不表示不用 ARIA，而是错误的角色或状态会覆盖原本正确的信息，使辅助技术用户得到错误答案。

### 名称、角色、状态与键盘行为

- **可访问名称（accessible name）**：回答“它叫什么”。优先让可见文字或关联的 `label` 提供名称；必要时使用 `aria-labelledby` 引用页面上已有文字，最后才考虑只对辅助技术可见的 `aria-label`。不要让可见名称“保存”与 `aria-label="提交订单"` 相互矛盾。
- **角色（role）**：回答“它是什么”。原生元素通常已经提供正确角色，不要给 `button` 重复写 `role="button"`，也不要为了样式把链接伪装成按钮。
- **状态（state）**：回答“它现在怎样”。例如展开按钮的 `aria-expanded` 必须随面板同步变化，校验失败的输入可标记 `aria-invalid="true"`，不可操作时优先使用真实的 `disabled`。
- **键盘行为**：回答“如何操作”。Tab 用来在可操作元素之间移动；复合组件可能使用方向键管理内部焦点。自定义角色必须实现规范约定的按键、焦点可见性和禁用逻辑。

### `button` 与 `div` 的正确比较

| 能力 | 原生 `<button type="button">` | `<div role="button">` |
| --- | --- | --- |
| 默认角色 | 自动暴露 `button` | 需要手动声明 |
| Tab 焦点 | 默认可聚焦 | 需要 `tabIndex={0}` |
| Enter / Space | 浏览器提供一致的激活行为 | 两种按键都要实现，并防止 Space 滚页 |
| 禁用 | `disabled` 阻止焦点和激活并暴露状态 | `aria-disabled` 只表达状态，代码仍须阻止操作 |
| 表单提交 | `type="submit"` 可参与表单 | 没有原生提交行为 |
| 维护成本 | 平台持续提供兼容性 | 事件、焦点、状态都由应用维护 |

```html
<!-- 正确：行为与语义都由平台提供 -->
<button type="button" aria-expanded="false" aria-controls="filters">
  筛选条件
</button>

<!-- 只有确实无法使用 button 时才承担这些行为 -->
<div role="button" tabindex="0" aria-disabled="false">
  筛选条件
</div>
```

仅给后者绑定 `click` 是典型反例：鼠标可用不代表键盘可用，`role` 也不会生成点击行为。

### 带标签且可描述错误的表单

错误消息必须既能被看见，也能和对应控件建立程序化关系。`label[for]` 提供控件名称，`aria-describedby` 引用补充说明或错误；错误出现时同步 `aria-invalid`。如果消息是提交后动态插入的，可以在错误摘要或消息容器上谨慎使用 live region，但不要在用户每输入一个字符时制造连续播报。

```html
<form novalidate>
  <div>
    <label for="email">工作邮箱</label>
    <input
      id="email"
      name="email"
      type="email"
      autocomplete="email"
      aria-invalid="true"
      aria-describedby="email-hint email-error"
    />
    <p id="email-hint">用于接收面试安排。</p>
    <p id="email-error">请输入有效的邮箱地址，例如 name@example.com。</p>
  </div>
  <button type="submit">保存</button>
</form>
```

不要把 placeholder 当作标签：输入后它会消失，而且通常对比度较低。也不要只用红色边框表示错误，颜色无法说明错误内容或修复方式。提交失败后可把焦点移到错误摘要，或聚焦第一个无效字段；选择哪一种取决于表单长度，但都应避免突然打断尚未提交的输入。

## 项目应用

自动化检查能发现缺少名称、无效 ARIA 等确定性问题，却不能判断阅读顺序或交互是否合理。发布前至少完成以下人工验证：

- 只用键盘从地址栏开始操作：Tab 焦点顺序应符合 DOM、视觉和阅读顺序，没有正数 `tabindex`，焦点样式清晰，弹窗打开和关闭后的焦点位置可预测。
- 检查每张有意义图片的 `alt` 是否表达其在当前上下文中的目的；纯装饰图片使用空 `alt=""`，不要重复相邻标题，也不要把文件名当替代文本。
- 浏览器缩放到 **200%**，确认文字和控件没有被裁切或重叠，核心功能无需二维滚动即可使用；不要通过禁止缩放来掩盖响应式问题。
- 用屏幕阅读器快速浏览标题、区域、链接和表单控件，确认 accessible name、role、state 与屏幕视觉一致。
- 在高对比度或强制颜色模式下检查焦点环、错误提示和图标；颜色之外还要有文字或形状提示。

## 边界与反例

语义化不等于页面必须塞满地标：重复或嵌套错误的 `main`、大量无名称的 `region` 同样会增加导航噪声。视觉顺序也不应通过 CSS `order` 与 DOM 顺序彻底分离，因为键盘焦点和屏幕阅读器通常仍按 DOM 移动。

ARIA 不能修复所有问题。`aria-hidden="true"` 的祖先里不能留下可聚焦控件；给不可见内容添加标签也不会让它变得可操作。自定义下拉框若只模仿外观，却没有列表框的方向键、Escape、类型选择和焦点模型，通常不如原生 `select`。无障碍还受到文案、对比度、目标尺寸和认知负担影响，不能仅凭“扫描工具零报错”宣布完成。

## 面试回答

我会先选有正确语义和交互行为的原生 HTML，因为 `button`、`label`、`input` 等元素已经向可访问性树暴露名称、角色和状态，并提供键盘及焦点行为。只有原生元素无法表达组件语义时才使用 ARIA，而且 ARIA 只补充语义，不会自动实现事件、焦点管理或键盘交互。

实现时我会逐项核对：控件是否有与可见文案一致的 accessible name，role 是否准确，`aria-expanded`、`aria-invalid` 等 state 是否和界面同步，以及 Tab 和组件内部按键是否符合约定。表单使用真实 `label`，错误用 `aria-describedby` 关联并提供修复提示。验证不能只靠自动化；我还会做全键盘流程、屏幕阅读器抽查、替代文本审查以及 200% 缩放测试。这样评估的是用户能否理解并完成任务，而不只是代码里有没有 ARIA 属性。

## 深度追问

1. **为什么给 `div` 添加 `role="button"` 仍不等于原生按钮？** 因为角色只改变可访问性树中的语义；Tab 焦点、Enter/Space 激活、禁用行为和表单能力仍需代码实现。优先换成 `button` 才能得到平台的一致行为。
2. **`aria-label`、`aria-labelledby` 和可见文本如何选择？** 优先使用原生可见文本；需要组合页面现有文字时用 `aria-labelledby`；只有视觉设计确实没有可见名称时才用 `aria-label`，并保证它不与屏幕上的名称冲突。
3. **动态表单错误如何处理？** 用 `aria-invalid` 标记字段，以 `aria-describedby` 关联具体错误；提交后把焦点移到错误摘要或首个错误。需要即时通知时使用克制的 live region，避免每次按键都播报。
