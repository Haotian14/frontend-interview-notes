# 前端系统设计的表达框架

## 一句话结论

开放式设计题考察的不是"标准答案"，而是能否结构化地推进：澄清约束 → 给出骨架 → 讲清数据流 → 主动覆盖边界 → 说明权衡；最后一步的取舍分析才是区分度所在。

## 前置知识

请先阅读[状态归属与 Context 边界](/topics/state-architecture)。设计题里被追问最多的就是"这个状态放在哪里"，那一篇给出的分类可以直接拿来用。

## 核心机制

### 第一步：澄清与约束（3–5 分钟）

一上来就画组件树是最常见的失分点。先问：

- **规模与场景**：多少用户？内容型还是工具型？主要在移动端还是桌面端？
- **核心指标**：优化首屏（LCP）还是交互流畅（INP）？有没有 SEO 要求？
- **必须支持的能力**：离线？多语言？无障碍？富文本？实时协作？
- **约束**：团队规模、技术栈是否受限、上线时间。

问完**复述一遍**："我理解这是一个面向移动端为主的内容信息流，重点是首屏速度和滚动流畅度，需要 SEO，暂不考虑离线——对吗？"这一步本身就是考察点：它证明你在真实工作中会先对齐需求，而不是闷头做。

### 第二步：方案骨架

**先整体后细节**，让对方能跟上你的结构。通常包含：

- **渲染方式**：内容型且要 SEO → 服务端渲染 + 流式；工具型且登录后使用 → 客户端渲染；混合场景 → 按路由选择。
- **模块划分**：三到五个顶层模块，说明各自职责与边界。
- **技术选型**：只说关键的几个并给出理由，不要罗列全家桶。

一边说一边画草图（白板或共享文档），画出来的东西是后续讨论的锚点。

### 第三步：数据流

明确每一类状态的归属：

| 类型 | 归属 | 例子 |
| --- | --- | --- |
| 服务端数据 | 数据请求库（缓存 + 失效） | 信息流内容、用户资料 |
| 可分享状态 | URL 查询参数 | 筛选、分页、当前标签 |
| 客户端共享状态 | Context 或状态库 | 登录信息、主题、草稿 |
| 局部状态 | `useState` | 输入框、展开收起 |

同时说明**接口形态**：分页用游标还是页码（信息流要用游标，页码在数据变动时会漏项重复）、要不要预取下一页、返回结构是否便于增量更新。

### 第四步：边界场景

这一步最能区分"做过真实项目"和"只写过 demo"。主动展开：

- **状态维度**：加载中（骨架屏而非转圈）、空状态（带引导动作）、错误（可重试）、部分失败。
- **网络维度**：弱网、超时、离线、请求竞态、重复提交。
- **数据维度**：超长文本、缺字段、异常数值、分页边界。
- **权限维度**：未登录、登录过期、无权限的降级展示。
- **可访问性**：键盘操作、焦点管理、屏幕阅读器播报、对比度。
- **国际化**：文案长度变化、RTL 布局、时区与货币。

不必每条都展开，但要**主动提及**，然后挑一两个深入。

### 第五步：权衡取舍

给出至少两个方案的对比，说明你的选择和它的代价：

> "无限滚动实现有两条路。虚拟滚动只渲染可视区域，内存和渲染成本恒定，但实现复杂、对不定高内容不友好、会影响浏览器原生的页内查找。分页加载实现简单、SEO 友好，但用户需要额外操作。考虑到这是移动端信息流、item 高度相对一致，我选虚拟滚动，代价是需要处理高度估算和滚动位置恢复，我会用成熟库而不是自己写。"

最后**主动指出局限**："当前方案在超长列表回退时会丢失滚动位置，下一步可以把滚动位置和已加载页码存进 history state。"承认边界比假装完美更可信。

### 一个完整示例：设计评论系统

**约束**：面向移动端，需要 SEO，支持嵌套两层回复，日均百万级浏览。

**骨架**：首屏评论随页面 SSR 输出（SEO + LCP），后续分页在客户端加载；组件分为列表、单条、回复输入框、举报菜单四块。

**数据流**：评论列表用游标分页并交给数据层缓存；`sort` 和 `cursor` 放 URL；输入框内容是局部状态并做本地草稿持久化；发布走乐观更新，失败后回滚并保留输入内容。

**边界**：空状态引导首评；发布失败可重试；重复提交用请求去重加幂等键；超长评论折叠；被删除的父评论显示占位；未登录时点击输入框跳登录并回填草稿；键盘可完整操作；表情与多语言字符按字素而不是码元计数。

**权衡**：嵌套结构可以用递归组件（结构自然但深层性能差）或扁平化加 `parentId`（渲染可控但要自己组装树）。层级限制为两层，所以选扁平化，代价是多一层数据转换。

## 项目应用

1. 提前准备两三个自己做过的项目，按"背景 → 约束 → 方案 → 权衡 → 结果"的结构写成 300 字，练到能脱口而出。
2. 结果要**量化**："首屏 LCP 从 4.1 秒降到 1.8 秒（75 分位）"远好于"性能明显提升"。
3. 准备好回答"如果重做你会怎么改"。这个问题考察的是反思能力，说"没什么要改的"是明显减分。
4. 面试中每讲完一段就停下来确认方向："这部分我讲得够细吗？还是先往下走？"避免自己讲十分钟跑偏。
5. 不知道的直接说不知道，然后给出你会怎么查证或验证。**编造比承认更致命。**
6. 白板画图时先画框和箭头，把命名写清楚；结构清晰的图能替你说很多话。

## 边界与反例

"背一套架构模板"在追问面前会立刻崩塌。面试官会顺着你的方案问"如果数据量再大十倍呢"、"如果这个接口挂了呢"，模板答不了这些。

"技术选型越新越好"是常见误区。选型要回到约束：团队熟悉度、生态成熟度、维护成本都是真实变量，"因为它很流行"不是理由。

"设计题要讲得越多越好"也不对。三十分钟里讲不完所有细节，重要的是**结构完整 + 一两处深入**，而不是每处都浅尝辄止。

"只讲技术不讲人"会失分。真实项目里推进方案需要说服他人、协调排期、处理历史包袱，能讲清这部分的候选人明显更成熟。

最后，对方案的批评不是对你的否定。被指出问题时先理解再回应："你说得对，如果并发写入很频繁，乐观更新会有冲突，那我会加版本号做冲突检测"——展示的是协作能力。

## 面试回答

面对开放式设计题我用五步。

第一步是**澄清约束**：先问清用户规模、设备与网络分布、要优化的核心指标是首屏还是交互、有哪些必须支持的能力（SEO、离线、无障碍），然后复述一遍确认理解一致。这一步本身就是考察点。

第二步给**方案骨架**：先说整体分层和渲染方式的选择，比如内容型场景选服务端渲染加流式，再往下拆三到五个模块，让对方能跟上结构。

第三步讲**数据流**：明确每类状态放在哪里——服务端数据交给数据层管缓存和失效，可分享的界面状态放 URL，剩下的才是本地状态；同时说明接口形态，比如信息流用游标分页而不是页码。

第四步主动展开**边界场景**：空状态、错误、弱网、竞态、权限、可访问性、国际化。这部分最能区分做过真实项目和只写过 demo 的人。

第五步是**权衡**：任何设计题都没有唯一答案，我会给出至少两个方案的对比、我的选择和它的代价，最后主动指出当前方案的局限和演进方向。

整个过程我会一边说一边画，并在每个阶段停下来确认方向，而不是自己讲十分钟。

## 深度追问

1. **设计一个无限滚动信息流，状态和请求怎么组织？** 列表数据用游标分页交给数据请求库缓存，页码或游标同步进 URL 以支持刷新和回退；滚动位置存进 history state 以便返回时恢复；用 `IntersectionObserver` 触发下一页并做去重，避免快速滚动时重复请求；渲染用虚拟滚动控制 DOM 数量；发布或删除用乐观更新并在失败时回滚。
2. **临时加上"支持离线"的约束怎么调整？** 引入 Service Worker：静态资源用预缓存，接口数据按 stale-while-revalidate 存进 Cache Storage 或 IndexedDB；写操作进入本地队列并在恢复网络后重放，因此接口必须幂等；界面要明确展示离线状态和"待同步"标记；冲突处理策略（后写覆盖还是版本号检测）要提前和产品确认。
3. **怎么描述一个技术权衡？** 用"背景 → 备选方案 → 判断依据 → 选择与代价 → 结果"的结构。重点是判断依据必须与业务约束挂钩（用户设备分布、团队规模、上线时间），并且诚实说明代价和事后来看的不足，结果尽量量化。
