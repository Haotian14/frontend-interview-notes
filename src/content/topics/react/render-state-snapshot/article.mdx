# React 渲染与状态快照

## 一句话结论

一次渲染会用当次的 props、state 和上下文计算出一个 UI 快照；调用状态设置函数只是把下一次渲染的更新排入队列，不会改写当前事件处理函数已经捕获的值。理解快照、更新队列与组件身份，才能准确解释批处理、状态重置和派生状态失真。

## 前置知识

请先阅读[类型收窄与穷尽检查](/topics/type-narrowing)，理解如何用稳定的数据形状表达组件状态；它对应元数据中的 `type-narrowing` 前置专题。本文还默认读者会使用函数组件、JSX、`useState` 和事件处理函数。这里的“纯”不是说组件永远不使用副作用，而是渲染阶段对相同输入应计算出相同 JSX，副作用应留给事件或 Effect。

## 核心机制

React 调用组件函数时，会读取这一轮的 props 和 state，并返回 JSX。事件处理函数也是这次函数调用创建的闭包，因此它看到的是这次渲染固定下来的状态。一次渲染可以看成四步：

1. 某次交互或外部变化触发更新；
2. React 处理更新队列，为相关组件计算下一份 state；
3. React 再次调用组件，得到新的 UI 快照；
4. React 把与上次结果不同且需要落到宿主环境的部分提交到 DOM。

渲染阶段应只是计算。若在组件函数顶层修改 DOM、发请求或无条件设置 state，重新渲染就会重复这些动作，甚至形成更新循环。提交 DOM 与浏览器实际绘制也不是同一个时刻：React 完成提交后，浏览器仍按自己的渲染流水线决定何时展示像素。

### 当前 state 不会被就地改写

下面的三次直接更新都读取同一个 `count` 快照。若本轮 `count` 为 `0`，三个参数都是 `1`；React 批量处理后结果通常是 `1`，而不是 `3`。

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  function addThreeDirectly() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
    console.log(count); // 仍是本次渲染的 0
  }

  return <button onClick={addThreeDirectly}>{count}</button>;
}
```

需要连续变换同一状态时，应传入更新函数。React 处理队列时，将前一个更新的结果交给下一个更新函数，因此 `0 → 1 → 2 → 3`。

```tsx
function addThreeFunctionally() {
  setCount(previous => previous + 1);
  setCount(previous => previous + 1);
  setCount(previous => previous + 1);
}
```

直接更新并非错误。`setOpen(true)` 表达“下一状态就是 true”，不依赖队列中的前值，通常比函数式写法更直接；只有下一值依赖前一值时，函数式更新才是关键。

### 批处理与更新队列

React 通常等当前事件处理代码执行完，再统一处理其中的状态更新。这样一个点击里的多个 setter 不必造成多个中间 UI 提交，也不会出现只更新了一半的界面。批处理不是把 JavaScript 变量变成可变值，而是延后处理排入的更新。

队列里既可以有“替换为某个值”的更新，也可以有“根据前值计算”的更新。比如本轮 `number` 为 `0`：

```tsx
setNumber(number + 5);       // 替换为 5
setNumber(value => value + 1); // 在 5 上计算，得到 6
setNumber(42);               // 最后替换为 42
```

最终值是 `42`。不要依赖“setter 返回后 DOM 已同步变化”的假设；若下一步必须在提交后与外部系统同步，应使用适当的 Effect，若只是计算下一状态则留在更新函数里。

### 状态属于树中的位置、类型与 key

state 并不“存放在 JSX 标签里”，而由 React 按渲染树中的位置关联。前后两次渲染中，同一父级同一位置出现相同组件类型且 key 相同，React 会把它视为同一身份并保留状态；类型变化、位置变化或 key 变化会建立新身份并重置该子树状态。

```tsx
function Profile({ userId }: { userId: string }) {
  return <Editor key={userId} userId={userId} />;
}
```

这里切换 `userId` 会有意重置 `Editor` 的草稿。相反，数组中使用不稳定的索引 key，插入或排序后会把旧状态错误地配给另一条数据。key 只需在兄弟节点间稳定且唯一，不是传给组件的普通业务属性。

### 派生状态反模式

若 `fullName` 完全由当前 `firstName` 和 `lastName` 得出，就不应再保存一份 state 并用 Effect 同步。第二份可写数据会让一次逻辑变化变成两次渲染，还存在 Effect 尚未运行时的短暂旧值。

```tsx
// 反例：可计算的数据被复制为 state
const [fullName, setFullName] = useState('');
useEffect(() => {
  setFullName(`${firstName} ${lastName}`);
}, [firstName, lastName]);

// 正例：在当前快照内直接计算
const fullName = `${firstName} ${lastName}`;
```

昂贵的纯计算可在确有性能证据时用 `useMemo` 缓存；它仍是派生结果，不应成为另一份事实来源。若用户能够独立编辑该值，或需要保存某一历史时刻的快照，它才可能是独立 state。

## 最小验证与证据

把直接更新和函数式更新放到两个按钮中，从 `0` 各点击一次：页面应分别显示 `1` 和 `3`，事件处理函数内的日志都仍显示点击前的值。这个可观察结果同时验证了闭包快照、队列顺序和批处理，而不是只凭 setter 调用次数猜测结果。

再做身份实验：给同一个 `Editor` 输入草稿，保持相同类型和 key 触发父组件重渲染，草稿应保留；把 key 从 `alice` 改为 `bob`，草稿应回到初始值。React DevTools 中可确认前者是同一组件实例继续渲染，后者是旧实例卸载、新实例挂载。

最后在 React Profiler 记录派生状态反例。修改姓氏会先提交旧 `fullName`，Effect 再排入一次更新；改为渲染期计算后只需一次逻辑提交。Profiler 的提交次数和界面文本是可重复的验证证据。

## 项目应用

- 计数、分页游标和队列长度等“基于旧值推进”的状态使用函数式更新。
- 服务器实体以稳定业务 ID 作为 key；需要在实体切换时清空表单，可把该 ID 用作表单子树的 key，明确表达重置意图。
- 代码评审时寻找“一个 state 能否完全由其他 props/state 算出”。能算出的值删除同步 Effect，在渲染期计算。
- 异步回调要意识到闭包捕获旧快照：能用函数式更新解决就不要额外读取旧值，需要读取最新外部状态时重新设计数据流或使用恰当的 ref。

## 边界与反例

批处理的具体边界由 React 版本、根 API 和同步逃生机制影响，业务代码不应把“每个 setter 恰好对应一次渲染”当作契约。React 开发模式下的 Strict Mode 还可能额外调用渲染逻辑来暴露不纯代码，这不代表生产环境每次都提交两次。

函数式更新也不能修复可变对象。`previous.items.push(item); return previous` 仍返回同一引用且污染旧快照；应返回包含新数组的新对象。key 也不是通用的“强制刷新”按钮：随每次渲染随机变化会不断丢失输入、焦点和子树状态。

并非所有重复数据都是反模式。用户确认前冻结的订单报价、撤销栈里的历史值和正在编辑但尚未提交的草稿，都具有独立生命周期，不能简单用当前 props 重算。

## 面试回答

React 每次渲染都会用当次 props 和 state 计算一个 UI 快照，事件处理函数也闭包住这个快照。调用 setter 不会修改当前变量，而是把更新加入队列；React 通常在当前事件结束后批处理。连续的 `setCount(count + 1)` 都基于同一个旧值，而 `setCount(n => n + 1)` 会按队列依次接收前一个结果。React 又通过树位置、组件类型和 key 判断组件身份：身份相同就保留 state，变化就重置。能由当前输入纯计算的派生值应直接计算，避免 Effect 同步第二份事实来源。

## 深度追问

### 为什么连续三次直接更新通常只增加一次？

三次表达式都在同一个渲染闭包里求值，读到相同的 `count`，因此入队的是三个相同替换值。它不是“React 丢掉了两次点击”；真正需要连续累加时，应让每个更新函数接收队列中的前一结果。

### React 依据什么保留或重置状态？

核心是组件在渲染树中的身份：父级下的位置、元素类型与 key 一起决定前后是否匹配。相同身份复用 state；改变类型、移到另一位置或改变 key 会创建新身份。列表 key 不稳定会导致状态跟错数据。

### 什么时候派生值可以保存为 state？

当它不再只是当前输入的纯函数，例如用户可以独立编辑、需要记录历史快照，或来自外部系统并有自己的同步生命周期时，可以成为独立状态。仅仅“计算写起来方便”或“可能有点贵”不够；昂贵纯计算优先以性能数据决定是否记忆化。
