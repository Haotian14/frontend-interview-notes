# 协调算法与 key

## 一句话结论

React 按**同层位置 + 元素类型**决定是复用还是重建组件，`key` 是在同一层里给元素一个稳定身份；用索引作 key 会让状态错配到相邻项，而换一个 key 正是主动重置状态的标准手段。

## 前置知识

请先阅读[React 渲染与状态快照](/topics/render-state-snapshot)，理解状态存在于组件实例上而不是 JSX 里。协调决定的正是"这次渲染产出的元素对应哪一个实例"。

## 核心机制

### 两个假设

通用的树 diff 算法是 O(n³)，无法用于 UI。React 用两个启发式假设把它降到 O(n)：

1. **不同类型的元素会产出不同的树**。因此类型变了就直接卸载重建，不再深入比较。
2. **开发者可以用 `key` 标记哪些子元素在多次渲染间是稳定的**。因此列表重排不必逐个内容比对。

这两条假设对绝大多数 UI 成立，代价是当假设不成立时会出现"状态莫名其妙保留或丢失"。

### 位置与类型决定复用

```jsx
// 同位置、同类型 → 复用实例，Counter 内部的 state 保留
{isFancy ? <Counter theme="fancy" /> : <Counter theme="plain" />}

// 同位置、不同类型 → 卸载 div 子树，重建 section 子树，状态全丢
{isWide ? <div><Counter /></div> : <section><Counter /></section>}
```

第一个例子经常出乎意料：切换 `isFancy` 时人们期待"换了一个组件"，但 React 看到的是同一位置的同一类型，于是复用了实例和它的 state。想让它重置，给两个分支不同的 `key`：

```jsx
{isFancy ? <Counter key="fancy" theme="fancy" /> : <Counter key="plain" theme="plain" />}
```

反过来，把组件定义写在另一个组件内部是常见 bug：

```jsx
function Parent() {
  // 每次渲染都产生一个新的函数引用 → 类型不同 → 每次都重建，状态全丢
  function Child() { return <input />; }
  return <Child />;
}
```

组件必须定义在模块顶层。

### key 的真正职责

`key` 不是"消除控制台警告的字符串"，而是**身份标识**：

```jsx
// 反例：索引作 key
{todos.map((todo, index) => <TodoItem key={index} todo={todo} />)}

// 正确：稳定的数据 id
{todos.map(todo => <TodoItem key={todo.id} todo={todo} />)}
```

删除第一项时，索引方案下原来的第 1 项变成了第 0 项，而 React 看到 `key={0}` 依然存在，于是复用了那个实例——它内部的输入内容、展开状态、动画进度全都留在了错误的数据上。

规则细节：

- `key` 只需要在**兄弟节点之间**唯一，不需要全局唯一。
- `key` 不是 prop，组件内部读不到 `props.key`；需要用到就再传一个同值的普通 prop。
- 用 `Math.random()` 作 key 是最糟的选择：每次渲染都不同，导致完全重建，既丢状态又最慢。
- 需要 Fragment 带 key 时用完整写法 `<Fragment key={id}>`，简写 `<>` 不接受属性。

什么时候索引作 key 是可以的？列表**静态、不排序、不增删、项内无状态**——这三个条件同时成立时索引是稳定的身份。但这类列表往往也就不需要纠结 key。

### 用 key 重置状态

这是 key 最被低估的用法。当"props 变了就该重来一遍"时：

```jsx
// 切换用户时清空表单和草稿，而不是写 effect 去同步重置
<ProfileEditor key={userId} userId={userId} />

// 重新发起一次搜索时重置内部的分页与选中项
<SearchResults key={query} query={query} />
```

相比在 `useEffect` 里逐个 `setState` 重置，这个写法没有额外渲染、不会漏掉某个字段、也不会产生连锁更新，是[Hooks 规则与依赖数组](/topics/hooks-dependencies)里"你可能不需要 effect"的典型案例。

### 协调之外

协调只决定"复用还是重建"。真正要跳过渲染需要记忆化（`React.memo`、`useMemo`），这是另一件事，见[React 性能优化](/topics/react-performance)。

现代 React 的渲染是**可中断**的：并发特性下一次渲染可能被暂停、丢弃或重做，因此渲染函数必须是纯的。这也意味着"渲染了多少次"本身不是性能指标，提交（commit）与 DOM 操作才是。

## 项目应用

1. 列表项的 key 一律用后端返回的稳定 id。没有 id 时在数据进入前端时就生成一个（`crypto.randomUUID()`），而不是渲染时临时造。
2. 乐观更新的临时项也要有稳定的临时 id，服务端返回真实 id 后做一次替换映射，不要让 key 中途改变。
3. 组件定义永远在模块顶层；需要"参数化的组件"就用 props 或高阶函数，不要在渲染函数里定义组件。
4. 需要在某个值变化时重置子树状态，优先考虑 `key`，其次才是 effect。
5. 表单、可编辑表格、拖拽排序这类"项内有状态"的列表，key 错误的后果最严重，重点检查。
6. 用 React DevTools 的 Components 面板观察组件是否被卸载重建（state 归零、effect 重跑），验证 key 策略是否正确。

## 边界与反例

"虚拟 DOM 比直接操作 DOM 快"是错误的营销话术。虚拟 DOM 的价值是**让声明式编程可行**——你描述结果，框架负责找出最小改动；手写精确的 DOM 操作永远可以更快，但难以维护。

"key 变了只是重新渲染"低估了它的代价：key 变化意味着**卸载和重建**，effect 会重跑、DOM 节点会重建、焦点和滚动位置会丢失、CSS 过渡会被打断。当作重置手段是好的，当作刷新手段就太重了。

"React 会自动做深比较"不成立。协调只比较元素类型和 key，props 的比较是浅层的，`React.memo` 默认也是浅比较。

同层比较意味着**跨层级移动节点无法被识别**：把一个子树从 A 移到 B，React 会卸载再创建，而不是移动。需要保持状态就避免改变组件在树中的位置。

最后，列表渲染的性能瓶颈通常不是 diff，而是**渲染了太多项**。一万行的表格应当用虚拟滚动，而不是优化 key。

## 面试回答

React 的协调基于两个假设，把 O(n³) 的树 diff 降到 O(n)：不同类型的元素会产出不同的树；开发者可以用 `key` 标记哪些子元素在多次渲染间是稳定的。

具体规则是按同层位置比较：位置和元素类型都相同就复用同一个实例，保留它的 state 和 DOM 节点，只更新 props；类型不同就卸载整棵旧子树再重建，状态全部丢失。所以条件渲染两个同类型组件时状态会被意外保留，而把组件定义写在渲染函数里会导致每次都重建。

`key` 的作用是在同一层里给元素一个身份标识，让 React 在顺序变化时知道谁是谁。用数组索引作 key 在静态列表里没问题，一旦可以增删或排序，索引和数据的对应关系就会错位，表现为输入内容、勾选状态跳到相邻项上。key 只需在兄弟之间唯一，也不会作为 prop 传给组件。

反过来，key 也是**主动重置状态**的正规手段：给组件换一个 key 就能让 React 卸载重建，比写 effect 逐个字段重置干净得多。

## 深度追问

1. **索引作 key 为什么导致状态错乱？** 因为 key 表达的是"这是同一个东西"。删除或插入后，同一个索引对应的数据变了，但 React 依据 key 认为组件没变，于是复用了实例，其内部 state 和未受控 DOM 状态就留在了错误的数据旁边。
2. **key 需要全局唯一吗？组件能读到吗？** 只需要在同一组兄弟节点内唯一。`key` 是 React 保留的特殊属性，不会出现在 `props` 里；需要在组件内使用同一个值就额外传一个普通 prop。
3. **怎么用 key 重置状态？** 把"应当触发重来一遍"的值作为 key 传给组件，例如 `<ProfileEditor key={userId} />`。值变化时 React 卸载旧实例、创建新实例，所有内部 state 与 effect 都重新开始，无需手写重置逻辑。
