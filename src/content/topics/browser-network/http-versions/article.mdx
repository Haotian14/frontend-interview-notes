# HTTP 版本演进与连接

## 一句话结论

三代协议的主线是**消除队头阻塞**：HTTP/1.1 靠多开连接、HTTP/2 用多路复用解决应用层阻塞、HTTP/3 换掉 TCP 解决传输层阻塞；每一步都让上一代的"优化技巧"变成负担。

## 前置知识

请先阅读[HTTP 缓存与重新验证](/topics/http-cache)，理解请求与响应的基本结构。本文关注的是这些请求**如何在连接上传输**，以及这对前端的资源组织策略意味着什么。

## 核心机制

### HTTP/1.1：一条连接一次一个

HTTP/1.1 是文本协议，一条 TCP 连接在同一时刻只能处理一个请求—响应对。管线化（pipelining）试图改善但因为响应必须按序返回而失败，实际上被所有浏览器禁用。

结果是浏览器对**每个域名**只开六到八条连接。一个有 80 个资源的页面，请求会排成明显的阶梯。当年的优化全部围绕"绕开这个限制"：

- **域名分片**：把资源分散到 `static1.`、`static2.` 等多个域名，换取更多并发连接。
- **雪碧图**：把几十个小图标合成一张大图，用 `background-position` 定位。
- **合并文件**：把所有 JS 打成一个包、所有 CSS 打成一个文件。
- **内联小资源**：把小图标转成 data URI 塞进 CSS。

每一条都在用别的成本换请求数。

### HTTP/2：多路复用

HTTP/2 改成二进制分帧：请求和响应被切成帧，标记流 ID 后在**同一条连接**上交错传输，接收端按流 ID 重组。于是：

- 一条连接可以同时承载几十上百个请求，**应用层队头阻塞消失**。
- 头部用 HPACK 压缩，重复的 `Cookie`、`User-Agent` 不再每次全量发送。
- 支持流优先级（浏览器可以声明 CSS 比图片重要）。

上一代的技巧随之失效甚至有害：

| 老技巧 | 在 HTTP/2 下的问题 |
| --- | --- |
| 域名分片 | 每个域名要单独建连和 TLS 握手，且分散了连接复用与头部压缩上下文 |
| 雪碧图 | 改一个图标就让整张图失效，且必须全量下载 |
| 合并成一个大包 | 改一行代码让整包缓存失效，首屏也要下载用不到的代码 |
| 内联 data URI | 无法单独缓存，base64 还膨胀约 33% |

**服务端推送**（Server Push）曾被寄予厚望，但因为无法知道客户端已缓存什么而经常推送浪费，主流浏览器已移除支持；替代方案是 `103 Early Hints` 配合 `preload`。

### HTTP/3：换掉传输层

HTTP/2 仍然跑在 TCP 上。TCP 保证**有序交付**：一个包丢失时，后面已经到达的数据必须等重传完成才能交给应用。于是同一条连接上的所有流一起被阻塞——这就是**传输层队头阻塞**，在丢包率高的移动网络下尤其明显。

HTTP/3 基于 QUIC（跑在 UDP 上）：

- **流之间真正独立**：一个流丢包不影响其它流的交付。
- **握手更快**：QUIC 把传输握手与 TLS 1.3 握手合并，新连接 1-RTT，恢复连接可以 0-RTT。
- **连接迁移**：连接由连接 ID 标识而非四元组，从 Wi-Fi 切到蜂窝网络时不需要重新建连。

代价是 UDP 在部分网络中被限速或阻断，因此客户端通常先用 HTTP/2 连接、通过 `Alt-Svc` 头发现 HTTP/3 后再升级。

### 对前端的实际影响

优化重点从"减少请求数"转向"**减少字节数 + 正确的优先级**"：

```html
<!-- 提前完成 DNS、TCP、TLS，为关键第三方域省下一个往返 -->
<link rel="preconnect" href="https://cdn.example.com" crossorigin />

<!-- 声明关键资源，提升发现时机与优先级 -->
<link rel="preload" as="font" type="font/woff2" href="/fonts/sans.woff2" crossorigin />

<!-- LCP 图片提高优先级 -->
<img src="/hero.avif" fetchpriority="high" width="1600" height="900" alt="…" />
```

分包策略也要重新权衡：太大则缓存粒度差、首屏冗余；太碎则请求虽然便宜但仍有解析与调度成本，且不利于压缩（更小的文件压缩率更低）。经验值是把稳定的第三方依赖、路由级代码、共享工具分开，单个 chunk 控制在几十 KB 量级，见[代码分割与按需加载](/topics/code-splitting)。

## 项目应用

1. 先确认线上实际协议：DevTools Network 面板打开 Protocol 列，或看 `h2`/`h3` 标记。很多"HTTP/2 优化"在源站仍是 1.1 时是无效的。
2. 部署到支持 HTTP/2 及以上的 CDN，静态资源与 API 尽量收敛到同一个域，减少建连与 CORS 复杂度。
3. 移除历史遗留的域名分片和雪碧图；小图标改用 SVG sprite 或独立文件。
4. 关键第三方域用 `preconnect`（数量控制在两三个以内，每个都占用连接资源）；确定要用的关键资源用 `preload`。
5. 用 `fetchpriority` 表达真实优先级：LCP 图片 `high`，首屏之外的图片 `low`。
6. 用 WebPageTest 或 Lighthouse 的瀑布图验证改动，不要只看本地开发环境——本地几乎没有延迟和丢包，协议差异完全体现不出来。

## 边界与反例

"升级到 HTTP/2 就快了"过于乐观。如果瓶颈是巨大的 JavaScript 包、阻塞渲染的 CSS 或慢接口，协议帮不上忙。协议解决的是**并发与排队**，不是字节数和执行时间。

"HTTP/2 下请求数不重要了"也不对。每个请求仍有服务端处理、解析、优先级调度成本，几百个小文件依然会拖慢；只是不再需要为了并发限制而合并。

"HTTP/3 一定更快"取决于网络。低丢包的有线网络里它与 HTTP/2 差别很小；高丢包、高延迟、频繁切换网络的移动场景收益才明显。部分企业网络会阻断 UDP，此时会回落到 HTTP/2。

"域名分片完全没用了"在极端情况下有例外（例如需要绕过单连接的并发流上限），但对绝大多数站点是净损失。

最后，连接层优化的收益上限由**首字节时间**和**关键渲染路径**决定，见[浏览器渲染流水线](/topics/rendering-pipeline)与[Core Web Vitals 与性能测量](/topics/web-vitals)。

## 面试回答

这条演进线的主题是**消除队头阻塞**。

HTTP/1.1 一条连接同一时刻只能处理一个请求，后面的必须排队，浏览器只好对每个域名开六到八条连接。于是产生了域名分片、雪碧图、合并文件、内联小资源这些绕开并发限制的技巧。

HTTP/2 引入二进制分帧和多路复用，同一条连接上可以有很多个流并行，头部用 HPACK 压缩，还支持流优先级。应用层队头阻塞消失，前面那些技巧随之失效甚至有害——合并破坏缓存粒度，分片增加握手成本。

但 HTTP/2 仍跑在 TCP 上，一旦丢包，TCP 为保证有序交付会阻塞这条连接上的所有流，这是**传输层**的队头阻塞。HTTP/3 把传输层换成基于 UDP 的 QUIC，流之间真正独立，还把 TLS 握手合进传输握手，新连接 1-RTT、恢复 0-RTT，并支持连接迁移，切换网络时不断线。

对前端的实际影响是：优化重点从减少请求数转向减少字节数和安排优先级——用 `preconnect` 提前建连、用 `preload` 和 `fetchpriority` 表达重要性、用合理的分包提高缓存命中率。

## 深度追问

1. **为什么不再推荐雪碧图和域名分片？** 多路复用之后并发不再是瓶颈，而这两项各自有明确代价：雪碧图让一个图标的改动使整张图缓存失效且必须全量下载；域名分片让每个域名单独建连和 TLS 握手，还分散了连接复用与 HPACK 的压缩上下文，整体是净损失。
2. **HTTP/2 为什么没彻底解决队头阻塞？** 它只解决了 HTTP 层：多个流在一条连接上交错传输。但底层 TCP 保证字节流有序，一个报文丢失时后续已到达的数据必须等待重传，导致所有流一起停顿。要解决必须换传输层，这就是 QUIC 的动机。
3. **HTTP/3 在移动端的实际收益？** 一是丢包时只影响单个流，弱网下的加载更平滑；二是 0-RTT 恢复让二次访问几乎立刻开始传输；三是连接迁移——从 Wi-Fi 切到蜂窝时连接 ID 不变，不用重新握手，视频和长连接场景体验差别明显。
