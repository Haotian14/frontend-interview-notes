# 浏览器渲染流水线

## 一句话结论

页面从响应字节变成像素，关键依赖链是 DOM/CSSOM → 样式 → 布局 → 绘制 → 合成；一次改动从它影响的最早阶段开始，通常还会连带后续阶段，因此优化前应先用性能记录确认瓶颈，而不是把所有视觉变化都笼统称为“重排重绘”。

## 前置知识

请先阅读[事件循环与任务队列](/topics/event-loop)，理解任务、微任务与渲染机会之间的关系；它对应元数据中的 `event-loop` 前置专题。本文还默认读者知道 HTML 元素形成 DOM 树、CSS 选择器为元素匹配规则，以及盒模型的内容、内边距、边框和外边距。层叠顺序的详细规则可在[层叠上下文与 z-index](/topics/stacking-context)中继续学习。

## 核心机制

用户输入 URL 后，浏览器通常经历 URL 解析、缓存判断、必要的 DNS/TCP/TLS 建连与 HTTP 请求，取得响应状态、头部和正文。缓存命中可能省掉部分或全部网络阶段，但无论字节来自网络还是本地缓存，HTML 都要被解析成可供页面使用的结构。

HTML 解析器按标准的分词与树构建规则增量生成 DOM。遇到外部样式表时，浏览器请求并解析 CSS，形成可用于规则匹配的 CSSOM；脚本是否阻塞解析取决于其属性、类型和所处位置。真实实现会预加载、并行下载和增量处理，所以“先完整下载 HTML，再完整构建 DOM，然后才下载 CSS”只是错误的串行简图。

得到足够的 DOM 与样式信息后，页面更新大致沿下面的依赖流推进：

1. **样式计算（style）**：解析层叠、继承和选择器匹配，得到元素的计算样式。
2. **布局（layout）**：根据视口、盒模型、字体和流式关系计算几何尺寸与位置；祖先尺寸变化可能影响大量后代。
3. **绘制（paint）**：把背景、文字、边框、阴影等转换为绘制记录，解决片段应画什么。
4. **合成（composite）**：把已经栅格化的图层纹理按变换、透明度和层级组合成最终画面。

这是一条依赖关系，不是保证每帧完整执行的固定流水账。只改变某些可合成属性时可以复用已有绘制结果；改变几何信息通常必须重新布局，并使受影响区域重新绘制和合成。浏览器还可能合并工作、局部失效或采用不同分层策略。

### 属性变化通常从哪一阶段开始

| 变化示例 | 通常需要的阶段 | 原因与提醒 |
| --- | --- | --- |
| `width`、`height`、`padding` | 样式 → 布局 → 绘制 → 合成 | 几何变化会影响自身和相关节点的位置；影响范围取决于布局关系 |
| `color`、`background`、`box-shadow` | 样式 → 绘制 → 合成 | 几何通常不变，但像素内容改变 |
| `transform`、`opacity` | 样式 → 合成（理想情况） | 合适的已提升图层可复用纹理；分层、内存和绘制仍由浏览器决定 |
| 添加或删除 DOM 节点 | 样式 → 可能布局 → 可能绘制 → 合成 | `display: none` 子树与脱离文档流元素的影响范围不同 |
| `z-index` 或层叠上下文条件 | 样式 → 可能绘制/合成 | 绘制顺序和分组可能改变，不等于必然创建独立 GPU 图层 |

表中的“通常”很重要。同一属性在不同元素、布局模式和浏览器实现中可能产生不同失效范围，最终应以 DevTools 的 Layout、Paint 和合成记录为证据。

### 强制同步布局：写后立刻读

DOM 和样式写入后，浏览器可以先标记布局失效，等本轮脚本结束后统一计算。但若脚本马上读取依赖最新几何的属性，为返回正确值，浏览器可能被迫立即完成待处理的样式和布局。循环交替写、读会产生 layout thrashing。

```js
// 反例：每轮写入后读取，可能反复强制布局
for (const card of cards) {
  card.style.width = containerWidth + 'px';
  console.log(card.offsetHeight);
}
```

先集中读取，再集中写入，可以让浏览器批量处理失效工作：

```js
// 正例：先读完旧布局，再统一写
const heights = cards.map(card => card.offsetHeight);

cards.forEach((card, index) => {
  card.style.width = containerWidth + 'px';
  card.dataset.previousHeight = String(heights[index]);
});
```

若写入依赖新布局，应重新审视算法，或把确需下一帧进行的写入安排到 `requestAnimationFrame`。它能对齐渲染时机，却不能让昂贵布局自动变便宜。

### 渲染机会不保证实际渲染

事件循环到达渲染相关步骤时，用户代理会判断当前是否是渲染机会。这个判断可以考虑显示刷新率、页面是否可见、浏览上下文状态和性能预算。即使出现渲染机会，也可以因为文档无需更新等条件跳过实际样式、布局或绘制；反过来，一次更新也可能包含多个文档和多类观察者、动画回调工作。

因此，“每完成一个任务就绘制一帧”和“`requestAnimationFrame` 固定每 16.7ms 执行”都不成立。高刷新率屏幕、后台标签页、长任务和系统负载都会改变间隔。正确表述是：浏览器在合适的渲染机会运行更新步骤，只有需要且允许更新时才产生可见结果。

## 最小验证与证据

在包含数百个卡片的测试页中，分别运行“循环写后读”和“先读后写”两个版本，用浏览器 Performance 面板录制。错误版本通常会在脚本调用栈中出现重复的 Recalculate Style/Layout，且单次交互总耗时显著上升；修正版通常把布局工作合并。记录中的事件数量、总布局时长和长任务标记，才是强制布局判断的证据。

验证动画时，对相同元素分别动画 `left` 与 `transform: translateX(...)`，开启 Paint flashing 和 Layers/Performance 观察。`left` 版本往往出现布局和更多绘制，合适分层的 transform 版本可能主要执行合成。若 transform 版本仍绘制，不应篡改结论，应检查图层尺寸、效果属性和浏览器的实际分层决定。

还可以在前台、后台标签页分别记录 `requestAnimationFrame` 时间戳。后台回调通常降频或暂停，直接反驳“每个渲染机会必定绘制、回调恒定 60Hz”的说法。

## 项目应用

- 先用 Performance trace 找到长任务、Layout 和 Paint 的具体调用栈，再决定改 JavaScript、DOM 规模、CSS 还是资源加载。
- 把一批测量集中到变更之前；滚动、拖拽时缓存不随帧变化的几何数据，避免每个节点反复读写。
- 动画优先考虑 transform 和 opacity，但用实际设备确认合成效果与内存成本，不滥用 `will-change`。
- 缩小布局与绘制影响范围：减少无关 DOM，使用合适的布局结构，并在确有隔离需求时评估 `contain`。
- 首屏问题要同时查看网络瀑布、主线程解析/执行和渲染记录；下载快不代表主线程能及时产出像素。

## 边界与反例

“重排一定触发整页重绘”过于绝对。浏览器会跟踪失效区域，独立子树和现代布局也可能限制影响；但局部失效仍有成本。反之，没有 Layout 事件也不代表免费：大面积绘制、纹理上传和合成同样可能掉帧。

transform 和 opacity 不是无条件的性能通行证。创建过多大图层会消耗显存，复杂滤镜、裁剪和混合效果可能要求额外离屏绘制；文字在变换下还可能出现视觉质量差异。`will-change` 应短期、针对性使用，而不是给所有元素永久开启。

DOM、CSSOM、render tree、layout tree 和 layer tree 是不同抽象，不应混称为一棵“渲染树”。规范定义处理模型和可观察行为，具体树结构、线程划分与图层提升是浏览器实现细节。

## 面试回答

浏览器取得 HTML 后按解析规则增量构建 DOM，并把 CSS 解析成 CSSOM。页面更新的主要依赖是样式计算、布局、绘制和合成：宽高等几何属性通常从布局开始并连带后续阶段，颜色通常需要绘制，合适图层上的 transform/opacity 常可只合成。脚本写样式后立即读 `offsetWidth` 等几何值，会迫使浏览器提前结算待处理布局，所以应先批量读、再批量写。事件循环到达渲染机会只表示可以考虑更新，不保证一定绘制；页面不可见、刷新节奏或无需更新都可能让实际工作被跳过。

## 深度追问

### 为什么读取 `offsetWidth` 可能触发强制同步布局？

它必须返回当前几何尺寸。若此前的 DOM 或样式写入已使布局失效，浏览器不能用旧尺寸回答，只能先同步完成相关样式和布局。单独读取并非必然昂贵，危险模式是循环中反复让布局失效后再读取。

### transform 动画为什么通常比 width 动画平滑？

width 改变盒子几何，常会影响邻近元素并触发布局、绘制和合成。已在合适图层上的 transform 可以移动已有纹理，主要由合成阶段处理。但“通常”不等于保证，图层创建、栅格化、内存与视觉效果仍需测量。

### 渲染机会等于一定绘制一帧吗？

不等于。渲染机会是用户代理考虑执行渲染更新的时点，实际是否更新还受文档是否需要渲染、可见性、刷新节奏和资源约束影响。`requestAnimationFrame` 也会随这些条件节流，不应当作固定频率计时器。
