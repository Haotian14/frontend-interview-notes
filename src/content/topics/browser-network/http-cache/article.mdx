# HTTP 缓存与重新验证

## 一句话结论

HTTP 缓存的决策顺序是“能否存储 → 是否仍新鲜 → 能否验证”：新鲜副本可不经网络直接复用，过期副本可携带验证器请求并在收到 `304 Not Modified` 后复用已有响应体，而 `no-cache` 与 `no-store` 分别表示“复用前验证”和“不要存储”。

## 前置知识

请先阅读[浏览器渲染流水线](/topics/rendering-pipeline)，理解导航取得的 HTML、CSS 和 JavaScript 最终如何参与页面构建；它对应元数据中的 `rendering-pipeline` 前置专题。本文默认读者知道 HTTP 请求/响应由状态码、首部和正文组成，也知道同一个页面会请求入口 HTML 与多个静态资源。这里讨论的是 HTTP 语义缓存，不把 Service Worker Cache API、应用内存对象缓存或 CDN 私有配置混为同一种机制。

## 核心机制

缓存收到响应时，先依据请求方法、状态码和响应指令判断是否允许存储。允许存储不代表之后可以直接使用；每次复用还要计算响应的当前年龄，并和新鲜度寿命比较。对常见浏览器资源，`Cache-Control: max-age=3600` 表示从相应时间基准起，一小时内可视为新鲜。若响应经过共享缓存，`s-maxage` 可以覆盖共享缓存使用的 `max-age`。

年龄并不只是本地计时器从零开始。RFC 9111 定义了根据 `Date`、`Age`、传输时间和驻留时间校正当前年龄的算法，使中间缓存转发的响应不会错误地“返老还童”。`Expires` 也能提供绝对过期时间，但现代部署通常优先使用更明确的 `Cache-Control`。

### 新鲜副本：200 本地缓存复用

副本仍新鲜时，浏览器可以直接使用缓存的状态、首部和正文，不向源站发条件请求。开发者工具可能显示 `200 (from memory cache)` 或 `200 (from disk cache)`：

- 内存缓存通常访问更快，生命周期多与当前浏览器进程或页面会话相关；
- 磁盘缓存可跨导航甚至会话保存，但要经过磁盘与缓存索引；
- “memory/disk”是浏览器实现与开发者工具的观察标签，不是 HTTP 状态码或服务器发回的新响应。

两者共同点是没有为了这次复用完成一次服务器验证。不能因为面板显示 200 就断言一定经过网络，应同时检查 Size/Transferred、Timing 和服务端访问日志。

### 过期副本：验证器与 304

过期不等于必须重新下载完整正文。若缓存响应带有 `ETag`，客户端可发送 `If-None-Match`；带有 `Last-Modified` 时可发送 `If-Modified-Since`。服务器判断所选表示未变化，就返回不含完整表示正文的 `304 Not Modified`，缓存把 304 中需要更新的元数据合并到已有响应，再复用旧正文。

`ETag` 是服务器为某个表示生成的实体标签，可以表达比秒级修改时间更精确的变化；`Last-Modified` 简单且便于静态文件使用，但时间粒度、生成方式和时钟可能限制准确性。客户端同时发送两类条件时，`If-None-Match` 的判断优先，不能要求两个验证器都“命中”才返回 304。

304 仍然经过网络、服务器或中间缓存处理，并承担往返时延；它节省的主要是响应正文传输，而不是把请求变成零成本。若内容已改变，服务器返回带新正文和缓存元数据的 200，缓存替换旧表示。

### 常见 `Cache-Control` 指令

| 指令 | 是否可存储 | 复用要求 | 典型用途与误区 |
| --- | --- | --- | --- |
| `private` | 可以，仅限私有缓存 | 仍由 `max-age`、验证器等决定 | 用户个性化响应；不是“加密”或“绝不落盘” |
| `public` | 可以，明确允许共享缓存 | 仍需满足新鲜度/验证规则 | 即使响应通常不可共享，也授权共享缓存存储 |
| `no-cache` | 可以 | 每次复用前必须向源站成功验证 | 名字易误导；它不是“不要缓存” |
| `no-store` | 不应存储 | 无副本可复用 | 适合不应写入缓存的敏感响应；已有副本的清理还需单独考虑 |

这些指令可以组合。例如个性化 HTML 常见 `Cache-Control: private, no-cache`，允许浏览器保存正文但每次验证；带哈希静态资源常见 `Cache-Control: public, max-age=31536000, immutable`。不要机械地给所有接口添加 `no-store`，那会同时放弃本地复用和条件验证的收益。

### HTML 短验证，哈希资源长期不可变

前端部署要解决的核心是一致性：旧 HTML 不能长期引用已经删除的资源，新 HTML 也必须能找到与其构建匹配的脚本和样式。

入口 HTML 使用短 `max-age`，或使用 `no-cache` 配合 ETag，使导航很快发现新版本。`app.7c91a2.js` 这类内容哈希资源只要内容变化就产生新 URL，因此可设置一年 `max-age` 加 `immutable`；旧 HTML 仍能访问旧资源，新 HTML 自动引用新 URL。部署时应先上传新哈希资源，再发布 HTML，并保留旧资源一段足够长的回滚与会话窗口。

不带内容哈希却设置长期 immutable 会让修复无法及时到达用户。反过来，给每个哈希资源都 `no-cache` 会让本可零网络复用的资源不断产生验证往返。

## 最小验证与证据

在隔离的浏览器配置中打开 Network 面板并保留日志，第一次导航应看到资源从网络返回 200。立即普通刷新：仍在新鲜期的哈希资源应显示 memory/disk cache 且 transferred 接近零；把资源设为 `no-cache` 后刷新，应看到带 `If-None-Match` 或 `If-Modified-Since` 的网络请求和服务器 304。修改文件内容及 ETag 后再次刷新，应得到新 200 与新正文。

证据至少要同时保存三类信息：请求条件首部、响应状态/缓存指令、服务端访问日志。只看响应列表中的“200”无法区分源站响应与本地缓存复用；勾选 DevTools 的 Disable cache 会人为绕开正常缓存行为，也不能作为生产策略验证。

部署策略可做一次版本演练：先加载版本 A 并保持标签页打开，再发布版本 B，确认 A 的 HTML 仍能请求它的哈希资源；新导航应经 HTML 验证拿到 B，并加载 B 的新 URL。这个结果直接验证发布顺序与旧资源保留窗口。

## 项目应用

- 为每类资源写清楚所有权、是否含用户数据、允许的最大陈旧时间和失效方式，再生成缓存策略。
- HTML、配置清单和 Service Worker 脚本保持短缓存或强制验证；内容哈希的 JS/CSS/字体采用长新鲜期与 `immutable`。
- API 若可缓存，要确认 `Vary` 正确区分会改变表示的请求首部，并防止共享缓存存入用户私有内容。
- 监控 200、304、缓存命中率、传输字节与发布后资源 404；仅优化“命中率”可能掩盖陈旧内容风险。
- 变更 ETag 生成规则时检查压缩表示和不同内容协商结果，避免同一强验证器错误标识不同字节。

## 边界与反例

刷新行为、开发者工具和浏览器启发式缓存会影响观察结果；HTTP 允许在缺少显式新鲜度时使用启发式规则，因此“没写 Cache-Control 就一定不缓存”不成立。为可预测部署，应明确发送指令，而不是依赖浏览器猜测。

`private` 只限制共享缓存，不防止浏览器私有缓存存储，也不提供访问控制。敏感数据仍需要 HTTPS、正确认证授权，并根据威胁模型使用 `no-store`。同样，`public` 不表示任何人有权限读取响应，它只改变缓存可存储性。

304 不携带完整正文，因此不能单独渲染资源；它依赖客户端已经有可用副本。强制刷新、缓存淘汰或验证器不匹配都可能得到完整 200。Service Worker 还可能拦截请求并实施独立策略，此时必须分别检查 HTTP cache 与 Cache Storage。

## 面试回答

HTTP 缓存先判断响应能否存储，再用 Cache-Control 等元数据计算新鲜度。副本仍新鲜时可以直接从内存或磁盘复用，不发网络请求；过期后若有 ETag 或 Last-Modified，就分别通过 If-None-Match 或 If-Modified-Since 发条件请求，内容未变时服务器返回 304，客户端复用已有正文。no-cache 是允许存储但复用前必须验证，no-store 才是不应存储。部署上让 HTML 短缓存或每次验证以发现新入口，带内容哈希的静态资源使用长期 max-age 和 immutable，内容变化通过新 URL 失效。

## 深度追问

### `200 from memory cache` 与 304 的成本有什么区别？

前者通常没有这次源站验证和网络往返，浏览器直接复用本地完整响应；304 是一次真实条件请求，仍有连接、往返、服务器或中间缓存处理成本，只省下完整正文。开发者工具中的缓存标签不是协议状态，判断时要结合 Timing 和日志。

### `no-cache` 和 `no-store` 为什么不能混为一谈？

`no-cache` 允许保存响应，只禁止在未成功验证时复用，因此可利用 304。`no-store` 要求缓存不要存储该请求/响应，后续没有副本可以验证复用。若目标是不泄露敏感数据，单写 `no-cache` 并不足够。

### ETag 与 Last-Modified 同时存在时如何验证？

客户端可以同时发送 `If-None-Match` 和 `If-Modified-Since`，服务器评估时实体标签条件优先。ETag 适合精确区分表示，修改时间可作为兼容或后备信息；两者都应对应实际选择出的表示及其内容编码。

### 为什么 HTML 和哈希静态资源采用不同策略？

HTML 是指向当前构建资源的可变入口，需要快速发现更新；哈希资源的 URL 已包含内容身份，内容不变即可长期复用，内容变化自然生成新 URL。两者配合既避免每次下载大资源，也避免入口长期停留在旧版本。
