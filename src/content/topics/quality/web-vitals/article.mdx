# Core Web Vitals 与性能测量

## 一句话结论

LCP、INP、CLS 分别衡量加载、交互和视觉稳定；它们都是**真实用户侧的过程量**，所以判据是 RUM 的 75 分位，实验室数据只用于定位和回归。

## 前置知识

请先阅读[浏览器渲染流水线](/topics/rendering-pipeline)。三个指标全都建立在"什么时候绘制了什么"之上，不理解解析、样式、布局、绘制、合成这条流水线，就无法把指标翻译成可执行的改动。

## 核心机制

### LCP：最大内容绘制

视口内最大的那个内容元素（图片、视频封面、块级文本）完成渲染的时间点。良好阈值 **2.5 秒**（75 分位）。

排查时把它拆成四段，逐段找占比最大的：

1. **TTFB**：服务端响应时间。慢就查后端、数据库、SSR 渲染耗时、CDN 命中率。
2. **资源发现延迟**：LCP 元素多久才被发现。CSS 背景图、JS 动态插入的图片都要等到很晚；写在 HTML 里的 `<img>` 能被预加载扫描器提前发现。
3. **资源加载时间**：图片体积、格式、优先级。
4. **渲染延迟**：字体未就绪、JS 阻塞、水合（hydration）占用主线程。

对应的动作：LCP 图片写进 HTML、加 `fetchpriority="high"`、**不要**加 `loading="lazy"`、用 AVIF/WebP 并按视口给合适尺寸，见[响应式图片与媒体加载](/topics/responsive-images)。字体用 `font-display: swap` 或 `optional`，并 `preload` 关键字体。

### INP：交互到下次绘制

INP 衡量整个访问期间**从用户交互到下一帧绘制**的代表性延迟（通常取接近最差的那次），良好阈值 **200 毫秒**。它在 2024 年取代了 FID。

区别很关键：FID 只测**输入延迟**——从用户点击到事件处理器开始执行的等待时间，而且只看第一次交互。INP 覆盖三段：

```text
输入延迟（主线程忙，事件排队）
  → 处理时间（事件处理器执行 + 状态更新 + 重渲染）
    → 呈现延迟（样式、布局、绘制、合成到屏幕）
```

所以一个"点击后要跑 300ms JavaScript 才更新列表"的按钮，FID 可能很漂亮，INP 却很差。常见成因：

- 长任务阻塞主线程（第三方脚本、大包解析、水合）。
- 事件处理器里做了昂贵计算或同步布局读取（读 `offsetHeight` 后又写样式，触发强制同步布局）。
- 一次交互触发了整棵组件树的重渲染。

改进手段：把长任务切分并让出主线程（`scheduler.yield()`、`setTimeout` 分片）、把重计算搬到 Web Worker、用 `useTransition`/`useDeferredValue` 让紧急更新优先、长列表虚拟化，见[React 性能优化](/topics/react-performance)。

一个便宜有效的技巧是**先给视觉反馈再做计算**：点击后立刻切换按钮状态并 `await` 一帧，让浏览器有机会绘制，再执行重活。

### CLS：累积布局偏移

页面生命周期内所有**非用户触发**的布局偏移得分之和（按会话窗口取最大值），良好阈值 **0.1**。

主要来源与解法：

| 来源 | 解法 |
| --- | --- |
| 图片、视频没写尺寸 | 写 `width`/`height` 属性或 CSS `aspect-ratio` |
| 广告、嵌入内容 | 预留固定高度的容器 |
| 动态插入的横幅、提示条 | 用绝对定位或覆盖层，不要挤压现有内容 |
| 字体替换（FOUT） | `font-display: optional` 或让回退字体的度量对齐 `size-adjust` |
| 先渲染骨架再换真实内容 | 骨架尺寸与真实内容一致 |

用户交互后 500ms 内的偏移不计入（`hadRecentInput`），因为那通常是用户预期中的变化。

### 怎么测

**实验室数据**（Lighthouse、WebPageTest、CI 里的 Playwright 跑分）：环境可控、可复现、能做回归门禁，但用的是模拟网络和固定设备，测不到真实用户的设备分布、网络状况、缓存状态和第三方脚本的实际表现。而且 Lighthouse 无法测 INP（没有真实交互）。

**真实用户数据（RUM）**：这才是判据。

```js
import { onLCP, onINP, onCLS } from 'web-vitals';

function send(metric) {
  navigator.sendBeacon('/rum', JSON.stringify({
    name: metric.name,
    value: metric.value,
    rating: metric.rating,
    id: metric.id,
    path: location.pathname,
  }));
}

onLCP(send);
onINP(send);
onCLS(send);
```

自己观测也不难：

```js
new PerformanceObserver(list => {
  for (const entry of list.getEntries()) {
    if (!entry.hadRecentInput) cls += entry.value;
  }
}).observe({ type: 'layout-shift', buffered: true });
```

**看 75 分位，不看平均值**。性能问题集中在长尾——低端设备、弱网、冷缓存。平均值会被大量快速访问稀释，掩盖掉那 25% 的糟糕体验。同时要按设备类型、地区、页面类型分组，否则"整体变好"可能只是流量结构变了。

## 项目应用

1. 先接 RUM 再优化。没有真实数据的优化是猜测，也无法证明收益。
2. 在 CI 里加 Lighthouse 或体积预算作为回归门禁（例如"首屏 JS 不超过 170KB 压缩后"），阻止性能悄悄劣化。
3. 优化按顺序做：确认 TTFB 正常 → 让 LCP 元素尽早被发现并快速加载 → 削减和延后 JavaScript → 给所有会变化的区域预留尺寸 → 再抠细节。
4. 第三方脚本单独评估：用 `async`/`defer`，能延后就延后，能自托管就自托管，并定期审计谁还在用。
5. 每次发布后对比核心指标的 75 分位，把性能纳入发布检查项而不是季度专项。
6. 指标异常时结合[前端错误监控与稳定性](/topics/error-monitoring)的数据一起看——很多性能骤降其实是某个接口开始报错重试。

## 边界与反例

"Lighthouse 90 分就没问题了"不成立。它是单次模拟，既测不到 INP，也代表不了真实用户分布。分数适合做相对比较，不适合当作达标证明。

"CLS 只要首屏不跳就行"忽略了它统计**整个生命周期**：无限滚动、懒加载内容、动态插入的提示都会持续累加。

"INP 差是因为设备慢"往往是推卸责任。低端设备正是大多数用户的真实设备，主线程预算本来就该按它们来定。

指标之间存在**权衡**：为了 LCP 内联首屏 CSS 会增大 HTML；为了 CLS 预留空间可能出现空白区域；为了 INP 延后水合会让交互在早期不可用。要按业务目标取舍，不要盲目追三个绿灯。

最后，Core Web Vitals 是**用户体验的代理指标**，不是目标本身。转化率、跳出率、任务完成时间才是目的；有时候把一次接口调用从 800ms 降到 200ms，比把 CLS 从 0.12 优化到 0.09 有意义得多。

## 面试回答

核心指标有三个，分别对应加载、交互和视觉稳定。

**LCP** 是视口内最大内容元素的渲染时间，良好阈值 2.5 秒。排查时拆成四段：TTFB、资源发现延迟、资源加载时间、渲染延迟，找占比最大的那段。常见修法是把 LCP 图片写进 HTML 并加 `fetchpriority="high"`、绝不给它加 `lazy`、用现代格式和合适尺寸、预加载关键字体。

**INP** 取代了 FID，衡量整个访问期间从交互到下一帧绘制的代表性延迟，阈值 200 毫秒。它包含输入延迟、处理时间和呈现延迟三段，所以长任务、事件处理器里的重计算和同步布局读取、一次交互引发全树重渲染都会拖垮它。改法是切分长任务并让出主线程、把计算搬进 Worker、用并发特性让紧急更新优先、长列表虚拟化。

**CLS** 是非用户触发的布局偏移得分之和，阈值 0.1，主要来自没写尺寸的图片、动态插入的横幅和字体替换。

测量上要区分实验室数据和真实用户数据：Lighthouse 可复现、适合 CI 回归，但测不到 INP 也不代表真实用户；真正的判据是 RUM 的 **75 分位**，因为性能问题集中在低端设备和弱网这些长尾场景，平均值会把它们稀释掉。

## 深度追问

1. **INP 与 FID 的区别？** FID 只测第一次交互的**输入延迟**，即事件排队等待的时间，处理器一开始执行它就结束了；INP 覆盖整个访问期间的所有交互，并且计入处理时间和呈现延迟，直到下一帧绘制。因此"点击后要算很久才更新"的页面 FID 很好而 INP 很差，替换后指标更贴近用户感受。
2. **LCP 慢从哪查？** 按四段拆：TTFB（服务端与 CDN）、资源发现延迟（LCP 元素是否写在 HTML 里、是否被 CSS 或 JS 延后发现）、资源加载时间（体积、格式、优先级、是否被其它请求抢占带宽）、渲染延迟（字体、阻塞脚本、水合）。哪段占比大就先改哪段。
3. **为什么看 75 分位？** 性能分布是长尾的，问题集中在低端设备、弱网和冷缓存用户身上。平均值会被大量快速访问拉低，看不出这部分体验；75 分位意味着"四分之三的访问不差于这个值"，既能反映多数人的体验，又不会被极端异常值主导。
