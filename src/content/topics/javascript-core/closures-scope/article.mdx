# 作用域链与闭包

## 一句话结论

JavaScript 的标识符解析由代码的书写位置决定，函数在创建时就记住了自己所处的词法环境；闭包就是这条环境引用在函数返回后依然有效，因此它保存的是**变量绑定**而不是某一刻的值快照。

## 前置知识

本文默认读者写过函数、循环和回调，知道 `var`、`let`、`const` 三种声明形式的基本写法。不需要预先理解事件循环，但如果你想弄清“回调是什么时候读到那个变量的”，可以配合阅读[事件循环与任务队列](/topics/event-loop)：闭包决定回调**能看到哪个绑定**，事件循环决定它**什么时候执行**，两者共同解释了异步代码里最常见的意外。

## 核心机制

### 词法环境与作用域链

每次进入一段可执行代码，引擎都会创建一个**词法环境**（Lexical Environment）。它包含两部分：记录本层声明的**环境记录**，以及指向外层环境的引用。

解析一个标识符时，引擎先查当前环境记录，找不到就沿外层引用继续向上，直到全局环境；仍找不到才抛出 `ReferenceError`。这条查找路径就是作用域链。

关键在于**外层引用在函数创建时确定，而不是调用时**：

```js
const label = 'module';

function outer() {
  const label = 'outer';
  return function inner() {
    return label; // 解析到 outer 的绑定，与谁调用它无关
  };
}

const fn = outer();
fn(); // 'outer'
```

把 `fn` 传到任何地方调用，结果都不变。这就是词法（静态）作用域，与 `this` 的动态绑定规则完全不同——`this` 看调用点，标识符看书写位置。

### 闭包保存绑定，不是值

函数值持有它创建时那个词法环境的引用。只要函数还可达，环境就不能被回收，于是外层函数返回后，内部函数仍能读写外层变量：

```js
function createCounter() {
  let count = 0;
  return {
    increment() { return ++count; },
    read() { return count; },
  };
}

const counter = createCounter();
counter.increment(); // 1
counter.increment(); // 2
counter.read();      // 2
```

`increment` 和 `read` 闭包住**同一个** `count` 绑定，因此互相可见。`count` 在函数外部无法直接访问，这是模块模式和私有状态的基础。

注意措辞：闭包捕获的是绑定，不是值。下面这段常被误读：

```js
let value = 'first';
const read = () => value;
value = 'second';
read(); // 'second'，不是 'first'
```

### 循环里的 `var` 与 `let`

这是闭包最经典的观察点：

```js
for (var i = 0; i < 3; i += 1) {
  setTimeout(() => console.log(i), 0);
}
// 3, 3, 3

for (let j = 0; j < 3; j += 1) {
  setTimeout(() => console.log(j), 0);
}
// 0, 1, 2
```

`var i` 是**函数级**的单个绑定，整个循环共享它；三个回调闭包住同一个绑定，等它们执行时循环早已结束，`i` 已是 `3`。

`let j` 则由规范规定：`for` 语句每轮迭代创建一个新的环境记录，并把上一轮的值复制进来。三个回调分别闭包住三个不同的绑定，所以各自保留了当轮的值。

在 `let` 出现之前，人们用 IIFE 手工制造这个每轮独立的环境：

```js
for (var k = 0; k < 3; k += 1) {
  (function (captured) {
    setTimeout(() => console.log(captured), 0);
  })(k);
}
// 0, 1, 2
```

理解了这一点就会明白：`let` 不是“修复了 `setTimeout`”，而是改变了绑定的创建时机。

### 提升与暂时性死区

三种声明都会在进入作用域时被登记，但初始化时机不同：

- `var` 登记并立即初始化为 `undefined`，所以声明前读取得到 `undefined`；
- `let` 和 `const` 登记但**不初始化**，从作用域开始到声明语句之间是**暂时性死区**（TDZ），此间读取抛 `ReferenceError`；
- 函数声明整体提升，可以在声明前调用。

```js
function demo() {
  console.log(hoisted); // undefined
  console.log(dead);    // ReferenceError: Cannot access 'dead' before initialization
  var hoisted = 1;
  let dead = 2;
}
```

TDZ 不是“`let` 不提升”，而是提升了却拒绝在初始化前被读取——这正是它比 `var` 更容易暴露顺序错误的原因。

## 最小验证与证据

把上面循环的两段代码直接贴进浏览器控制台，观察输出是 `3,3,3` 还是 `0,1,2`。这是最快、最不依赖工具的验证。

要观察闭包的内存效应，用 DevTools 的 Memory 面板：拍一次堆快照，创建大量闭包住大数组的回调后再拍一次，用 Comparison 视图查看 `(closure)` 条目的保留大小（Retained Size）。解绑这些回调并强制 GC 后第三次拍照，保留大小应回落；如果没有回落，说明还有引用链把环境留住了。

Sources 面板的 Scope 区域也能直接印证作用域链：在内部函数里下断点，可以看到 Local、Closure、Script、Global 分层，Closure 一栏列出的正是被捕获的绑定。

## 项目应用

- 用闭包实现私有状态（计数器、缓存、一次性初始化），比在对象上挂 `_private` 约定更可靠。
- 防抖、节流、记忆化这类高阶函数都依赖闭包保存定时器句柄或缓存表；参见[防抖与节流的实现与取舍](/topics/debounce-throttle)。
- React 的事件处理函数闭包住当次渲染的 props 和 state，这正是[React 渲染与状态快照](/topics/render-state-snapshot)里“陈旧闭包”问题的根源；理解绑定捕获才能判断何时需要函数式更新或 ref。
- 长期存活的监听器、订阅和定时器要在卸载时解绑，否则它们闭包住的整个环境都无法回收。
- 只捕获真正需要的变量：从大对象里先解构出需要的字段再进入闭包，可以让其余部分被回收。

## 边界与反例

**闭包本身不是内存泄漏。** 泄漏发生在“不再需要却仍然可达”的时候。一个被正确解绑的闭包和普通对象一样会被回收；真正的问题是忘记 `removeEventListener`、忘记 `clearInterval`，或把回调塞进全局集合再也不取出。

**闭包不会复制外层变量。** 常见误解是“闭包保存了当时的值”，循环里的 `var` 案例恰好证伪了它。需要值快照时必须显式复制（参数传入、解构或 `let` 的每轮绑定）。

**性能不是回避闭包的理由。** 现代引擎对闭包分配有充分优化，创建闭包的开销远小于绝大多数业务逻辑。只有在被反复执行的极热路径上，且有 profile 证据时，才值得考虑把函数提到外层复用。

**块级作用域不等于每次都新建环境。** 只有在块内实际存在 `let`/`const`/`class` 声明，并且被闭包捕获时，才需要为它保留独立环境；引擎可以对没有捕获的情况做优化。不要据此推断某种写法“一定更省内存”。

## 面试回答

JavaScript 是词法作用域：标识符解析看代码写在哪里，不看谁调用。函数在创建时就持有所处词法环境的引用，这个引用在外层函数返回后依然有效，就形成了闭包。要点是闭包捕获的是变量**绑定**而不是值副本——循环里用 `var` 时三个回调共享唯一的函数级绑定，所以都读到终值 3；用 `let` 时规范要求每轮迭代创建新绑定，所以各自读到 0、1、2。闭包的代价是被引用的环境不能回收，因此长期存活的事件监听、定时器和缓存要在不需要时解绑，并尽量只捕获需要的字段。日常最常用它来做私有状态、防抖节流和记忆化。

## 深度追问

### 闭包保存的是值还是绑定？

是绑定。同一个绑定被后续代码修改后，闭包读到的是新值。循环中 `var` 与 `let` 的差异不是“闭包行为不同”，而是两者创建绑定的数量和时机不同：`var` 整个循环一个函数级绑定，`let` 每轮迭代一个新绑定。

### 什么情况下闭包会造成内存无法回收？

当闭包本身仍然可达，而它捕获的环境里含有大对象时。典型来源是未解绑的事件监听器、未清除的 `setInterval`、被全局数组或 Map 长期持有的回调，以及缓存了 DOM 节点的闭包（节点已从文档移除但仍被闭包引用，形成游离 DOM）。判断标准始终是可达性，而不是“用没用闭包”。

### TDZ 和 `var` 提升在行为上有什么不同？

`var` 在进入作用域时就被初始化为 `undefined`，因此声明前读取是合法的、得到 `undefined`，错误往往在更远处才暴露。`let`/`const` 同样被提前登记，但保持未初始化状态，声明前读取直接抛 `ReferenceError`，错误在发生点立刻暴露。TDZ 是一种主动的错误前置，不是“没有提升”。

### 为什么 React 里会出现“陈旧闭包”？

因为事件处理函数和 effect 回调都是某一次渲染期间创建的，闭包住那一次的 props 和 state 绑定。异步回调执行时，组件可能已经重新渲染多次，但这个函数仍读取创建它那轮的绑定。解决方向是让下一状态由更新函数从队列中推导，或用 ref 持有需要跨渲染读取的最新值。
