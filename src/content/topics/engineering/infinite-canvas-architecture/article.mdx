# 无限画布的状态与渲染架构

## 一句话结论

先稳定世界坐标、状态分层、命令历史和可见性查询，再选择 DOM、Canvas 或混合渲染；如果这些基础边界不清晰，吸附线、图层和 AI 排版越多，系统越难维护。

## 前置知识

请先阅读[浏览器渲染流水线](/topics/rendering-pipeline)和[前端系统设计的表达框架](/topics/frontend-system-design)。无限画布不是一个“大组件”，而是文档模型、几何系统、输入系统、渲染器和持久化之间的协作。

## 核心机制

### 四层状态不要混在一起

**文档状态**是可保存、可撤销、可协作的事实：节点 id、类型、世界坐标、尺寸、旋转、层级和业务属性。

**视口状态**描述用户怎么看文档：平移 `tx/ty`、缩放 `scale`、画布容器尺寸。除非产品明确要求恢复视角，它不应进入文档版本。

**选择状态**包括选中 id、主选中项、正在文本编辑的节点，通常是会话级 UI 状态。

**瞬时交互**包括 pointer 起点、拖拽预览矩阵、套索框、候选吸附线。它每帧变化，不应每次写入全局 store、撤销栈或后端。

将四层揉成一个巨大对象，任何 pointermove 都会让订阅者重新计算，也无法回答“撤销一次应该撤销什么”。

### 世界坐标与视口矩阵

文档节点永远使用世界坐标。简单平移缩放下：

```ts
type Viewport = { tx: number; ty: number; scale: number }

function worldToScreen(point, viewport) {
  return {
    x: point.x * viewport.scale + viewport.tx,
    y: point.y * viewport.scale + viewport.ty,
  }
}

function screenToWorld(point, viewport) {
  return {
    x: (point.x - viewport.tx) / viewport.scale,
    y: (point.y - viewport.ty) / viewport.scale,
  }
}
```

节点旋转、嵌套组和非中心缩放应统一使用二维矩阵及其逆矩阵，而不是到处手写偏移。缩放围绕鼠标位置时，要保证缩放前后鼠标指向同一个世界点，再反推新的平移量。

### 输入系统

统一使用 Pointer Events 处理鼠标、触摸和触控笔。pointerdown 后调用 `setPointerCapture`，即使指针移出元素也继续接收 move/up；记录 `pointerId`，不要让第二根手指意外接管当前拖拽。

一次拖拽建议分三段：

1. pointerdown：命中测试、确定操作模式、记录初始快照；
2. pointermove：屏幕坐标转世界坐标，计算预览变换并在 rAF 合帧；
3. pointerup/cancel：提交一条语义命令，释放捕获并清空瞬时状态。

移动事件频率可能高于屏幕帧率，直接每次 render 没有价值。保存最后一次指针位置，在下一帧最多处理一次。

### 渲染方案选择

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| DOM/SVG | 文本、表单、无障碍和调试简单 | 节点很多时布局、样式和内存成本高 |
| Canvas 2D | 大量图元统一绘制，控制明确 | 命中、文本编辑、可访问性都要自建 |
| WebGL | 海量纹理和变换吞吐高 | 实现、资源管理和文字渲染复杂 |
| 混合 | Canvas 绘内容，DOM 覆盖编辑器与控件 | 两套坐标和层级必须严格同步 |

不要因为名字叫“画布”就默认 Canvas API。几百个可编辑 DOM 节点可能完全够用；数万个图元才需要更激进的渲染器。选择依据是元素规模、类型、交互和设备，而不是技术偏好。

### 可见性与命中测试

每帧遍历全部节点判断是否在视口内，复杂度会随文档线性增长。为节点维护世界坐标包围盒，并放进 R-tree、四叉树等空间索引：

- 视口查询得到需要渲染的候选；
- 点或小矩形查询得到命中候选；
- 再按 z-index 和精确几何做最终判断。

空间索引不是免费的。移动节点时要更新索引，批量拖拽可先用临时变换，结束后一次提交，避免每帧重建。

### 命令、撤销与保存

拖拽一百帧不应该产生一百条历史。命令记录语义起点和终点：

```ts
type MoveCommand = {
  type: 'move'
  ids: string[]
  before: Record<string, Point>
  after: Record<string, Point>
}
```

`execute` 应用 after，`undo` 恢复 before。命令同时可以成为自动保存的输入，但撤销历史与网络队列仍要解耦：保存确认不应删除本地撤销能力。

## 项目应用

1. 元素实体用 id 归一化存储，图层顺序单独保存，避免复制整棵树修改一个节点。
2. 拖拽只更新 overlay 或临时矩阵，pointerup 再提交文档状态，减少框架响应式传播。
3. 吸附线先从空间索引查询附近节点，再比较边、中心和间距；不要对全画布做两两比较。
4. 图片解码、缩略图和远处节点采用分级质量，视口外停止昂贵工作。
5. 建立性能场景：100、1000、10000 节点下测缩放、框选和批量移动的帧耗时与内存。
6. 对坐标转换写往返测试，对命令写 execute/undo 对称测试，这两类错误最适合用确定性单测拦截。

## 边界与反例

“所有状态都进 Pinia/Redux，方便统一管理”会让 pointermove 变成全局广播。瞬时交互可以放局部对象或专门控制器，只有最终语义状态才进入文档 store。

“只要加虚拟化就能支持海量节点”不够。看不见的节点不渲染解决的是绘制成本，命中测试、对齐计算、选择集合和资源解码仍可能全量工作。

“Canvas 一定比 DOM 快”忽略了需求。文本编辑、输入法、复制粘贴和可访问性在 DOM 上有大量免费能力，换成 Canvas 后需要自己重建。

“缩放就是给容器加 CSS transform”只解决视觉；事件命中、吸附阈值、线宽和编辑控件还必须理解屏幕与世界单位的差异。

## 面试回答

我会先把无限画布拆成文档、视口、选择和瞬时交互四层。文档模型保存节点、层级和世界坐标，可以撤销和持久化；视口只管平移缩放；选择属于会话 UI；拖拽起点、吸附线和预览矩阵是每帧变化的瞬时状态，不进入全局历史。

所有 PointerEvent 先通过视口逆矩阵从屏幕坐标转成世界坐标，渲染再走正向矩阵。输入层使用 pointer capture 保证拖出容器仍能正确结束，move 事件用 requestAnimationFrame 合帧，pointerup 时才形成一条语义命令。

渲染方案根据元素规模和交互选 DOM、Canvas 或混合。节点很多时用空间索引按世界包围盒查询可见节点和命中候选，不能每帧全量遍历。撤销栈保存命令的 before/after，自动保存消费同一语义变更，但两者生命周期独立。

## 深度追问

1. **为什么使用世界坐标？** 它让文档数据不依赖当前视角，同一个文件在不同设备和缩放下仍一致；事件和渲染只在边界做矩阵转换。
2. **什么时候选择混合渲染？** 大量图像和图形适合 Canvas/WebGL，但文本编辑、输入法和浮层控件适合 DOM 时，用同一视口矩阵同步两层。
3. **空间索引怎样维护？** 节点提交位置或尺寸变化时更新包围盒；高频预览期间可暂不写索引，结束后批量更新，再做精确几何命中。
4. **撤销为什么不保存每个 move？** 用户意图是“把节点从 A 移到 B”，中间采样只是输入过程；合成一条命令才能提供可理解的撤销和紧凑保存。
