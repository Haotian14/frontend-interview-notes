# 前端测试策略与分层

## 一句话结论

测试层级应由故障风险与反馈速度共同决定：让纯规则在单元层快速穷举，让组件集成测试覆盖用户可观察的协作，让少量 E2E 保护真实浏览器中的关键链路；测试越接近用户的名称、角色和行为，越不容易被无关重构击碎。

## 前置知识

请先阅读[语义化 HTML 与可访问性](/topics/semantic-accessibility)，理解可访问名称、角色和原生交互；它对应元数据中的 `semantic-accessibility` 前置专题。本文默认读者熟悉函数、组件、HTTP 请求与基本断言，也能区分产品需求和实现细节。测试工具示例使用 Vitest、Testing Library 与 Playwright，但选择原则不绑定某个框架。

## 核心机制

测试不是按“越多越安全”堆叠，而是为具体失败建立成本合适的探测器。先问四个问题：失败会造成多大业务或用户损失？该路径多久变化一次？哪一层能真实触发风险？失败后多快、在哪里得到反馈？

例如，金额舍入规则影响大、输入组合多且无需浏览器，应以毫秒级单元测试穷举边界；提交表单涉及验证提示、按钮状态和请求协作，组件集成测试更有信心；第三方登录重定向、Cookie 和跨页面结算只有真实浏览器链路才能覆盖，则需要少量 E2E。把所有内容提升到 E2E 会变慢且难定位，把一切拆成隔离单元又会错过组件之间的接线错误。

### 各层责任

| 层级 | 主要责任 | 适合验证 | 不应承担 |
| --- | --- | --- | --- |
| 单元测试 | 一个纯函数、状态转换或独立规则 | 边界值、错误分支、可辨识状态、算法不变量 | DOM/浏览器集成是否真实工作 |
| 组件/集成测试 | 多个真实模块在接近用户的环境中协作 | 表单交互、可访问输出、路由/状态/请求结果 | 所有浏览器与后端部署细节 |
| E2E 测试 | 已部署或完整启动的系统关键旅程 | 登录、支付、跨页导航、浏览器权限和真实接线 | 穷举每个业务计算与微小视觉分支 |

分层不是按文件命名。一个“组件测试”若把所有子组件和 hooks 都 mock 掉，实际只验证调用约定；一个直接调用多个真实领域模块的测试可能已经是集成测试。判断标准是它跨越了哪些真实边界、失败时能证明什么。

### 从用户可访问的角色查询

Testing Library 鼓励用接近用户使用方式的查询。下面的测试不关心按钮用了哪个 class，也不读取组件内部 state；它通过文本框的可访问名称输入，再通过按钮的角色与名称提交。

```tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { expect, test, vi } from 'vitest';

test('submits the email a user entered', async () => {
  const user = userEvent.setup();
  const submit = vi.fn();
  render(<InviteForm onSubmit={submit} />);

  await user.type(screen.getByRole('textbox', { name: '邮箱' }), 'dev@example.com');
  await user.click(screen.getByRole('button', { name: '发送邀请' }));

  expect(submit).toHaveBeenCalledWith({ email: 'dev@example.com' });
});
```

若查询失败，优先检查产品是否真的暴露了正确 label、role 和可见名称。`data-testid` 适合作为没有语义可查询对象的最后手段，例如无法通过角色表达的画布内部标记；它不应成为绕开可访问性问题的默认入口。

### 模拟外部边界，不模拟被测实现

测试需要控制不稳定或昂贵的外部边界，例如网络、系统时间、随机数、地理位置或第三方 SDK。边界内的解析、状态更新和真实子组件应尽量运行。以下测试替换浏览器的 `fetch` 边界，却渲染真实组件并观察用户可见结果：

```tsx
test('shows the server rejection to the user', async () => {
  vi.spyOn(globalThis, 'fetch').mockResolvedValue(
    new Response(JSON.stringify({ message: '邀请已存在' }), {
      status: 409,
      headers: { 'Content-Type': 'application/json' },
    }),
  );

  render(<InvitePage />);
  await userEvent.type(screen.getByRole('textbox', { name: '邮箱' }), 'dev@example.com');
  await userEvent.click(screen.getByRole('button', { name: '发送邀请' }));

  expect(await screen.findByRole('alert')).toHaveTextContent('邀请已存在');
});
```

更大的测试套件可以用协议级拦截器统一描述 API，而不是逐个 mock 数据 hook。反例是 mock `useInvite()` 返回某个内部对象，再断言组件调用了它：请求参数序列化、错误解析和加载状态都被替身绕开，测试即使全绿，真实接线仍可能坏。

E2E 中也应控制自身拥有的测试数据和服务状态，但尽量不要 mock 浏览器要验证的功能。Playwright 定位器优先使用 role、label 和稳定业务可见文本；每个测试隔离账号或数据，避免依赖执行顺序。

### 覆盖率不是质量证明

语句、分支和函数覆盖率回答“哪些代码被执行过”，不回答断言是否正确、需求是否遗漏或浏览器组合是否真实。一个不含断言的测试也能跑出高语句覆盖率；对 `if (isAdmin)` 只测试两个布尔值，也未必覆盖权限数据来源被篡改的风险。

覆盖率适合发现明显空白和监控意外下降，不适合作为唯一目标。优先级应结合：生产回归记录、代码变更频率、业务损失、不可逆操作、跨系统边界和人工发现难度。每个线上缺陷都应先找到最便宜且能真实复现它的层级，再添加回归测试。

## 最小验证与证据

一个测试必须先证明它能抓住对应故障。实现回归测试时，先在隔离分支或工作区引入/保留真实缺陷，运行目标测试看到它因用户可观察结果失败；再修复生产代码看到同一测试转绿。若测试在缺陷存在时仍绿，它只是执行了代码，没有保护需求。

角色查询示例可做一个具体实验：移除输入框关联的 `<label>`，测试应在 `getByRole('textbox', { name: '邮箱' })` 处失败；恢复 `htmlFor`/`id` 关联后转绿。这说明测试约束的是用户与辅助技术可感知的接口，而非源代码字符串。

对分层本身也收集证据：CI 记录各套件耗时、失败重试率、缺陷发现层级和 flaky 率。若一个 E2E 只验证纯计算却经常超时，把规则下沉到单元层并保留一条集成主路径；若组件测试常绿但部署后路由基路径反复失败，就补一条真实部署 E2E。

## 项目应用

- 从关键用户旅程和历史事故列出风险清单，为每项选择能真实触发它的最低成本测试层。
- 提交前运行相关单元/组件测试，CI 并行跑全量快速套件，少量关键 E2E 在合并与部署环境验证。
- 测试命名写出生产故障，例如“无障碍名称丢失时用户无法提交”，而不是“组件应该工作”。
- 建立测试数据工厂与固定时钟，避免复制巨大夹具；只暴露场景需要的字段，使失败原因清晰。
- 定期删除与需求重复且价值更低的测试。维护成本、执行时间和误报都会消耗团队对红灯的信任。

## 边界与反例

“不要测试实现细节”不等于永远不能断言技术接口。设计系统的公共 props、领域库导出的函数和协议序列化格式本身就是契约，可以直接验证；应避免的是对用户不可见、又不承诺稳定的内部 state、私有方法和调用顺序。

快照测试适合稳定、可审阅的小型结构或序列化输出，但巨大的 JSX 快照容易在评审中被盲目更新，不能替代行为断言。视觉回归擅长发现像素差异，却需要稳定字体、视口和基线治理，也无法单独证明键盘行为或业务结果。

E2E 少不等于完全没有，单元多也不等于固定金字塔比例。支付、权限、迁移等高损失链路值得更深的跨层冗余；低风险展示组件可能一个聚焦的组件测试就足够。策略必须随事故和架构变化调整。

## 面试回答

我按失败风险和反馈速度选择层级：纯规则用快速单元测试穷举，组件与真实依赖的交互用组件集成测试，跨页面、浏览器能力和关键业务链路用少量 E2E。查询尽量使用用户可感知的 role、label 和文本，这既降低对 class/DOM 结构的耦合，也能约束可访问接口。只 mock 网络、时间、随机数等外部边界，让被测实现真实运行。覆盖率只能说明代码执行过，不能证明断言质量；我会按生产回归、变更频率和业务损失确定优先级，并要求回归测试在修复前真实失败。

## 深度追问

### 组件测试和 E2E 的边界如何确定？

看故障是否依赖真实浏览器、部署配置或跨服务链路。表单验证、加载和错误 UI 可在组件环境快速覆盖；OAuth 重定向、Cookie 策略、真实路由基路径和支付回跳需要 E2E。保留 E2E 主路径，分支穷举下沉到更快层级。

### 为什么优先 `getByRole` 而不是 `data-testid`？

role 配合可访问名称接近用户和辅助技术找到控件的方式，重构 class 或包装层通常不会破坏它；缺失 label 时测试也会揭示真实可访问性问题。testid 是测试专用接口，只在没有合适语义查询时使用。

### 高覆盖率为什么仍可能漏掉严重缺陷？

覆盖工具只记录执行路径，不理解断言、需求与环境。测试可能执行支付失败分支却没有验证退款状态，也可能完全模拟掉真实序列化或浏览器权限。严重风险要由有意义的场景、真实边界和精确结果断言覆盖，而不是靠百分比推导。
