# 打包、Tree Shaking 与产物

## 一句话结论

Tree Shaking 不是打包器单方面的能力，而是**模块格式（ESM）、导入方式（具名）、副作用声明（sideEffects）**，三者同时成立的结果；任何一环缺失，未使用的代码都会原样进入产物。

## 前置知识

请先阅读[模块系统与 ESM](/topics/module-systems)。"静态可分析"是本文的核心前提；如果还不清楚 `import` 与 `require` 在解析时机上的差别，先回到那一篇。

## 核心机制

### 打包器在做什么

从入口出发，打包器完成五件事：

1. **解析依赖图**：读 `import`/`require`，递归找到所有模块。
2. **转换**：TypeScript、JSX、CSS、图片各有加载器或插件处理。
3. **优化**：Tree Shaking（删未引用的导出）、作用域提升（把多个模块合并进一个作用域减少函数包装）、常量折叠。
4. **分包**：按入口、动态 `import()`、以及配置的策略切分 chunk。
5. **压缩与产出**：minify、生成 Source Map、写入带内容哈希的文件名。

现代工具（Vite、Rspack、Turbopack）在**开发**时通常不打包或只做极轻的处理，靠浏览器原生 ESM 提供快速启动；**生产**构建才走完整流程。这意味着**开发环境的体积和加载表现不具参考性**。

### Tree Shaking 的三个条件

**条件一：ESM。**

```js
import { formatDate } from 'date-utils';   // 可静态分析：只用了 formatDate
const utils = require('date-utils');       // 无法分析：整个模块必须保留
```

`import`/`export` 是语法结构，名字是字面量、位置固定在顶层，打包器不执行代码就能建立引用关系图。这是 Tree Shaking 的根本前提。

**条件二：具名导入。**

```js
import { debounce } from 'lodash-es';      // 好：只保留 debounce
import * as _ from 'lodash-es';            // 差：命名空间被整体使用
import _ from 'lodash';                    // 最差：CommonJS 默认导出，全量打入
```

`lodash` 与 `lodash-es` 的差别是很多项目里最直接的几十 KB。

**条件三：没有未声明的副作用。**

打包器面对一个未被引用的模块时必须判断"删掉它安全吗"。如果模块顶层有 `window.x = 1`、修改原型、注册自定义元素、导入 CSS，删掉就会改变程序行为。由于静态分析无法可靠判定，打包器默认**保守保留**。库作者用 `package.json` 明确告知：

```json
{
  "name": "my-ui",
  "sideEffects": false
}
```

```json
{
  "sideEffects": ["*.css", "./src/polyfills.js"]
}
```

前者表示"我的任何模块都可以放心删除"，后者列出确有副作用的文件。**标错的后果很严重**：明明需要的 polyfill 或样式被删掉，本地开发（不做 Tree Shaking）一切正常，线上却缺样式或报错。

### 为什么"只用一个函数还是很大"

按可能性排序排查：

1. 这个库只发布了 CommonJS 产物（看 `package.json` 有没有 `exports`/`module` 字段指向 ESM）。
2. 用了默认导入或命名空间导入。
3. 库没有 `sideEffects` 声明，或声明为有副作用。
4. 库内部是一个大文件，导出之间互相引用，删不干净。
5. 你导入的函数确实依赖了库的大半功能（例如国际化数据、时区表）。
6. 类的方法通常删不掉——只要类被实例化，未使用的方法也会保留。这是"函数导出比大类更利于 Tree Shaking"的原因。

解法依次是：换库（`dayjs`/`date-fns` 替代 `moment`）、改成按子路径导入、或者接受体积并把它切进单独的 chunk 异步加载。

### 产物分析

```bash
# Vite / Rollup
npx vite build && npx vite-bundle-visualizer

# 或在配置里接入 rollup-plugin-visualizer
```

看三件事：

- **总体积与首屏 chunk 体积**（压缩后 gzip/brotli 的数字才有意义）。
- **单个依赖的贡献**，特别是"没想到它这么大"的那些。
- **重复打包**：同一个库出现多份（版本不一致、ESM 与 CJS 双份），这也是[模块系统与 ESM](/topics/module-systems)里说的双包危险。

### 压缩之外还有传输层

产物再小，也要确认服务端开启了 Brotli 或 gzip、静态资源带内容哈希与长期缓存、HTML 不被缓存。这些配置错误造成的浪费往往比代码优化大得多，见[HTTP 缓存与重新验证](/topics/http-cache)。

## 项目应用

1. 在 CI 里记录并对比产物体积，设置预算（例如首屏 JS 压缩后不超过某个阈值），超出直接失败，见[CI 质量闸门与发布](/topics/ci-quality-gates)。
2. 引入新依赖前先查体积（bundlephobia 之类）和是否提供 ESM 产物；一个 30KB 的库用来做一件小事通常不值得。
3. 自己的内部库一律输出 ESM、正确声明 `exports` 与 `sideEffects`、导出粒度用独立函数而不是巨型类。
4. 导入样式、polyfill 这类副作用模块时集中在入口文件，并在 `sideEffects` 中列出，避免被误删。
5. 定期跑一次可视化分析，把"体积最大的五个依赖"作为固定的技术债项。
6. 区分"删不掉"和"不该加载"：删不掉的大依赖可以用动态 `import()` 移出首屏，见[代码分割与按需加载](/topics/code-splitting)。

## 边界与反例

"Tree Shaking 会自动删掉所有没用的代码"过于乐观。它删的是**没有被引用的导出**，函数内部的死分支要靠压缩器的死代码消除，而运行时才能确定的分支（`if (config.feature)`）谁也删不掉。

"`sideEffects: false` 是万能加速开关"是危险的。它是一个**承诺**，不是优化选项；库里但凡有一处顶层副作用没声明，就会在生产环境产生难以复现的 bug。

"开发环境体积很大所以有问题"多半是误判：开发构建不压缩、包含 HMR 运行时和完整的 Source Map。任何体积结论都必须基于生产构建。

"打包器越新越快"忽略了瓶颈可能在别处：巨大的 `node_modules`、没有缓存的 CI、类型检查串行执行。先测量再换工具。

最后，体积只是手段。真正的目标是主线程工作量和用户可交互时间——一个 500KB 但可以延后加载的 chunk，危害小于一个 100KB 但阻塞首屏解析的脚本。

## 面试回答

打包器从入口出发解析依赖图，把模块转换、优化、合并、压缩成产物，并按配置切分 chunk。Tree Shaking 是其中的死代码消除步骤，它能生效需要三方配合。

第一是**模块格式必须是 ESM**：`import`/`export` 是静态语法，打包器不执行代码就能建立引用关系；CommonJS 的 `require` 是运行时表达式，只能保守保留整个模块。

第二是**导入方式**：具名导入才能精确到导出粒度，默认导入或命名空间导入等于用到了整个模块。

第三是**副作用声明**：打包器无法确定模块顶层代码有没有外部影响，所以库要在 `package.json` 里写 `sideEffects`，标为 `false` 表示可以放心删，或者列出确实有副作用的文件（样式、polyfill）。标错会导致必要代码被删掉——本地开发正常，线上缺样式或报错。

实践中我会用产物分析工具看每个依赖贡献了多少体积，重点排查"只用了一个函数却打进来几十 KB"的库，原因通常是它只发布 CommonJS 产物或内部有顶层副作用，这时换库或按子路径导入比调打包配置更有效。还要注意开发构建不做压缩，体积必须以生产构建为准。

## 深度追问

1. **Tree Shaking 为什么依赖 ESM？** 因为它需要在**不执行代码**的前提下知道"谁引用了什么"。ESM 的导入导出是顶层语法结构、名字是字面量，可以静态建图；CommonJS 的 `require` 路径和取值都是运行时表达式，静态分析只能保守处理，结果是什么都不敢删。
2. **`sideEffects` 标错会怎样？** 标成 `false` 但实际有副作用时，未被显式引用的模块会被删掉，表现为线上缺样式、polyfill 未注入、自定义元素未注册；而这些在不做 Tree Shaking 的开发环境完全正常，极难复现。反过来漏标（不写这个字段）只是体积偏大，不影响正确性。
3. **为什么只导入一个函数还是很大？** 常见原因是：库只有 CommonJS 产物、用了默认或命名空间导入、库未声明 `sideEffects`、库内部导出互相引用、或者这个函数本身依赖了大量数据（时区、语言包）。类的未使用方法通常也删不掉，所以函数式导出的库更利于 Tree Shaking。
