# CI 质量闸门与发布

## 一句话结论

把检查按"成本从低到高"排成闸门，让失败反馈尽可能早；发布侧用灰度、特性开关和秒级回滚把风险从"能否避免故障"变成"能多快止损"。

## 前置知识

请先阅读[前端测试策略与分层](/topics/testing-strategy)。CI 是把测试策略变成强制约束的地方；没有分层清晰的测试，流水线只会变成又慢又不可信的负担。

## 核心机制

### 闸门的顺序

原则是：**便宜的先跑，昂贵的后跑，能并行的并行**。

1. **确定性安装**：用锁文件（`npm ci` 而不是 `npm install`），缓存依赖目录。安装耗时经常是流水线里最大的一块。
2. **格式与 lint**：秒级，抓风格问题和明显错误。
3. **类型检查**：`tsc --noEmit`。它覆盖的是测试跑不到的组合，价值被普遍低估。
4. **单元与组件测试**：按文件分片并行。
5. **构建 + 体积预算**：产物能构建是底线；体积超过阈值直接失败。
6. **端到端与可访问性**：在预览环境跑关键路径，数量少而稳。

```yaml
# 示意：把独立任务拆开并行，而不是串成一条长链
jobs:
  static:   { steps: [install, lint, typecheck] }
  unit:     { steps: [install, "vitest run --shard 1/3"] }
  build:    { steps: [install, build, "size-limit"] }
  e2e:      { needs: build, steps: ["playwright test"] }
```

一条前端流水线控制在**几分钟**内是合理目标。超过十分钟，人们就会开始绕过它——用 `--no-verify` 提交、把失败的测试标记为 skip、或者干脆不看结果。**流水线的速度是它的可信度的一部分。**

### 闸门要有明确的失败标准

"打印警告但不失败"的检查等于不存在。每一条闸门都要能回答"什么情况下阻止合并"：

- lint 有 error → 失败；warning 不阻塞但计数不允许增长。
- 类型检查任何错误 → 失败。
- 测试失败或超时 → 失败；**不允许**用重试掩盖不稳定测试，不稳定的测试要么修好要么删掉。
- 首屏 JS 压缩后超过预算 → 失败，见[打包、Tree Shaking 与产物](/topics/bundling-tree-shaking)。
- 关键页面的可访问性自动检查（axe）出现严重问题 → 失败。

覆盖率是**诊断指标不是目标**。硬性要求 90% 覆盖率会催生大量断言薄弱的测试；更有用的做法是关注"新增代码是否有对应测试"和"关键路径是否被覆盖"。

### 预览环境

每个 PR 部署一个独立可访问的预览环境，收益很大：

- 评审可以直接点开看效果，而不是从 diff 里想象。
- 端到端测试跑在真实构建产物上，而不是开发服务器。
- 设计、产品、QA 可以在合并前介入。

### 发布：从"避免故障"到"快速止损"

**灰度（金丝雀）发布**：先把新版本放给 1% 的流量，观察错误率、核心指标和关键业务转化，再逐步放大到 10%、50%、100%。观察窗口要足够长，覆盖一个完整的用户行为周期。

**特性开关**：把"发布代码"和"启用功能"解耦。

```js
if (flags.newCheckout) {
  return <CheckoutV2 />;
}
return <CheckoutV1 />;
```

出问题时关掉开关即可，不必回滚整个版本，也不必等一次完整发布流程。代价是代码里会积累分支，所以每个开关都要有**清理计划和负责人**，否则半年后没人敢删。

**快速回滚**：回滚必须是秒级且演练过的。前端的关键是：

- 静态资源用内容哈希文件名，**保留旧版本一段时间**（否则回滚后旧 HTML 引用的文件已被清理）。
- HTML 入口不缓存或短缓存，保证切换立即生效，见[HTTP 缓存与重新验证](/topics/http-cache)。
- 数据库或接口的变更要向前兼容，否则前端能回滚而后端不能。

**把监控接进闭环**：发布事件标注在错误率与性能曲线上，某个版本上线后指标跳变就能立刻定位，见[前端错误监控与稳定性](/topics/error-monitoring)。

## 项目应用

1. 主分支保护：必须通过所有闸门才能合并，禁止直接推送。
2. 本地用 git hook 跑最快的一部分（格式化 + 变更文件的 lint），完整检查留给 CI；本地钩子太慢会被绕过。
3. 依赖更新用自动化工具（Renovate/Dependabot）小步进行，让 CI 承担验证；大版本升级单独开 PR。
4. 给每个产物打上 `release` 版本号（commit SHA 即可），并在构建时自动上传 Source Map。
5. 建立"发布检查清单"：灰度比例、观察指标、回滚方式、值班人。清单比经验可靠。
6. 定期审查流水线耗时与失败率。经常无故失败的闸门比没有闸门更糟——它会训练团队忽略红灯。

## 边界与反例

"闸门越多越安全"忽略了成本。每条闸门都要维护、都会误报、都在消耗每个人的等待时间。宁可少而可信，不要多而被忽略。

"覆盖率 100% 就没有 bug"是最经典的误用。覆盖率只说明代码被执行过，不说明断言有意义；把它当 KPI 会直接损害测试质量。

"能自动化的都自动化"要看性价比。视觉回归测试维护成本很高，UI 频繁变动的项目容易变成噪音源；先覆盖核心页面，不要全站铺开。

"CI 通过就可以上线"不成立。CI 验证的是代码，线上还有数据形态、流量规模、第三方依赖和用户设备分布这些变量——这正是需要灰度和监控的原因。

最后，特性开关不是免费的：它增加代码分支和测试组合，长期不清理会让代码库难以理解。**开关的生命周期应当以周计，不是以年计。**

## 面试回答

我把 CI 看成一组按成本从低到高排列的闸门，越便宜的越早跑，让失败反馈尽可能快。顺序一般是：确定性安装并缓存依赖 → lint 和格式检查 → 类型检查 → 单元与组件测试 → 构建并检查体积预算 → 在预览环境跑少量端到端和可访问性用例。能并行的都并行，测试按文件分片。一条前端流水线控制在几分钟内是合理目标，超过十分钟大家就会开始绕过它。

闸门必须有明确的失败标准：体积超预算就直接失败，而不是打印一行警告让人忽略；不稳定的测试要么修好要么删掉，绝不用自动重试掩盖。覆盖率是诊断指标不是目标，硬性指标只会催生断言薄弱的测试。

发布侧我关注三件事：一是**灰度**，先放一小部分流量观察错误率和核心指标再逐步放大；二是**特性开关**，让发布和启用解耦，出问题关掉开关即可，不必回滚整个版本；三是**回滚要快且演练过**——静态资源保留旧版本、HTML 不缓存，这样回滚才是秒级的。

最后把监控接进这个闭环：发布事件标注在错误率曲线上，异常时能立刻定位是哪个版本引入的。

## 深度追问

1. **闸门为什么按这个顺序？** 因为反馈速度本身就是价值。lint 和类型检查在一分钟内就能报出大部分低级错误，没必要等十分钟的端到端跑完才知道少写了一个分号。同时越靠前的检查越稳定、误报越少，把不稳定的昂贵检查放在后面，可以减少无谓的重跑。
2. **灰度和特性开关分别解决什么？** 灰度控制的是**新版本代码**的暴露范围，用来发现构建、依赖、性能层面的整体问题；特性开关控制的是**某个功能**的启用范围，粒度更细、切换更快，还能做定向放量和 A/B 实验。两者互补：灰度管版本，开关管功能。
3. **为什么不该把覆盖率当目标？** 覆盖率只统计代码是否被执行，不衡量断言是否有意义。把它设成硬指标时，最省力的达标方式是写大量"调用一遍不断言"的测试，结果是覆盖率漂亮但缺陷照样漏出，还增加了维护成本。更有价值的是关注关键路径覆盖和新增代码的测试情况。
