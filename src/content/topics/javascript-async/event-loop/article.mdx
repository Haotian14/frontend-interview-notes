# 事件循环与任务队列

## 一句话结论

事件循环让单线程 JavaScript 在不阻塞整个页面的情况下协调任务、微任务和渲染机会。

更准确地说，浏览器选择并执行一个任务，等它的调用栈清空后执行微任务检查点。渲染不是紧接在每个微任务检查点之后的固定阶段：窗口事件循环遇到渲染机会且页面需要更新时，会在渲染任务源中排入更新渲染任务，等待事件循环选择。

## 前置知识

先理解调用栈和 Promise 的状态变化。

- **调用栈**记录当前正在执行的函数。只有栈清空，本轮同步代码才算执行完毕。
- **任务**承载脚本执行、计时器回调和用户交互回调等工作。常说的“宏任务”通常就是指这类任务，但规范使用的是“任务”。
- **微任务**包括 Promise reaction 和 `queueMicrotask` 回调。它们在当前任务结束后的微任务检查点执行。
- Promise 状态变为 fulfilled 或 rejected 并不等于回调立即运行；`.then`、`.catch`、`.finally` 注册的 reaction 会通过微任务调度。

## 核心机制

稳定的顺序保证是：事件循环选择一个可运行任务，执行到调用栈清空，随后执行微任务检查点。此后继续选择哪个任务取决于事件循环调度，不能固定推导成“先渲染，再执行下一个任务”。

可以把浏览器事件循环理解为以下过程：

1. 从某个任务队列中选择一个可执行任务，例如初始脚本、点击回调或已到期计时器。
2. 执行该任务，期间普通函数不断入栈、出栈；异步 API 则登记后续工作。
3. 调用栈清空后执行微任务检查点。只要队列不为空就继续取出微任务，即使新微任务由旧微任务追加。
4. 事件循环继续选择可运行任务。窗口事件循环发现渲染机会且某个可渲染文档需要更新时，会把“更新渲染”作为全局任务排入渲染任务源。
5. 更新渲染任务被选择后才运行相应渲染步骤；`requestAnimationFrame` 回调在这些步骤中执行。这个任务完成后同样会到达微任务检查点。

任务不是按一个全局 FIFO 队列机械执行。HTML 定义了不同的任务源，包括用于更新渲染的任务源；浏览器可以在保证同一任务源顺序的前提下选择队列。因此可靠的推理依据应是“选中的任务执行完后进行微任务检查点”，而不是把所有异步回调想象成同一个队列，或假设每个普通任务后都有一个独立渲染阶段。

## 最小验证

```js
console.log('A');
setTimeout(() => console.log('B'));
Promise.resolve().then(() => console.log('C'));
console.log('D');
// A D C B
```

初始脚本本身是一个任务，所以先同步输出 `A` 和 `D`。脚本结束时，Promise reaction 已进入微任务队列，于是输出 `C`。计时器回调即使延迟参数为 `0`，也只能作为后续任务被选择，所以最后输出 `B`。

下面的例子说明微任务检查点会处理期间新加入的微任务：

```js
queueMicrotask(() => {
  console.log('microtask 1');
  queueMicrotask(() => console.log('microtask 2'));
});

setTimeout(() => console.log('timer'));
// microtask 1, microtask 2, timer
```

## 项目应用

长任务会延迟输入响应；持续创建微任务也会让渲染和后续任务得不到执行机会。

当一次数据处理、Markdown 解析或复杂渲染持续几十毫秒，主线程无法同时响应点击和输入。可以把工作按时间片拆分，并通过后续任务把控制权还给浏览器。`setTimeout` 能建立任务边界；支持的环境里也可以使用更适合调度工作的 API。拆分时要测量实际耗时，不能只按数组长度猜测。

微任务适合在当前任务结束后、浏览器观察到中间状态前完成少量收尾工作，例如批量通知观察者。它不适合承载大量计算：递归调用 `queueMicrotask` 或连续建立立即兑现的 Promise 链，会让微任务队列一直无法清空。

```js
function processInChunks(items) {
  const chunk = items.splice(0, 100);
  for (const item of chunk) processItem(item);

  if (items.length > 0) {
    setTimeout(() => processInChunks(items), 0);
  }
}
```

如果工作目的是更新视觉状态，应把 DOM 写入集中起来，并用 `requestAnimationFrame` 请求在下一次更新渲染步骤中执行，而不是用计时器猜测帧边界。它只登记回调；回调要等相应更新渲染任务被事件循环选中才会运行。

## 边界与反例

“微任务永远先于宏任务”并不准确，因为当前同步脚本本身就在一个任务中。

还要注意以下边界：

- `setTimeout(fn, 0)` 表示满足最小延迟后具备被调度的资格，不保证立即执行；嵌套计时器还可能受到延迟钳制。
- 渲染不是每完成一个任务就一定发生，也不是任务与任务之间必经的独立阶段。页面不可见、刷新率和浏览器调度策略都会影响渲染机会与更新渲染任务的调度。
- `requestAnimationFrame` 回调不是普通微任务，也不应简单背成“比计时器早”。它在更新渲染任务的相关步骤中执行，实际顺序取决于该任务何时被选择。
- 不同宿主的事件循环并不完全相同。浏览器模型不能原样套用到 Node.js 的各个阶段。

最危险的反例是无界微任务链：

```js
function starve() {
  queueMicrotask(starve);
}

starve();
```

每个微任务又排入下一个微任务，检查点无法结束，事件循环便无法选择后续任务，其中也包括已经排入或之后需要排入的更新渲染任务。真实项目必须设置终止条件，或改用能让出主线程的任务级调度。

## 面试回答

浏览器事件循环选择并执行一个任务，随后执行微任务检查点，因此当前脚本产生的 Promise 回调通常早于后续计时器任务。渲染没有固定插在两者之间；有渲染机会且需要更新时，浏览器会在渲染任务源排入更新渲染任务。

回答执行顺序题时，我会先标出当前同步任务，再记录它创建的微任务和后续任务。同步栈清空后执行微任务检查点，然后回到任务选择；若浏览器此前因渲染机会排入了更新渲染任务，它也要参与任务调度。这个模型解释了两个工程问题：长任务会阻塞交互，而无限微任务链会阻止事件循环选择包括更新渲染在内的后续任务。`requestAnimationFrame` 回调在更新渲染步骤中执行，不应被硬塞进普通任务或微任务队列。

## 深度追问

1. 为什么递归创建微任务会影响页面渲染？
2. requestAnimationFrame 位于哪个阶段？

第一问的关键是微任务检查点会持续处理新加入的微任务，直到队列为空；若始终追加，事件循环就无法选择后续任务，包括更新渲染任务。第二问应回答：回调在更新渲染任务的相关步骤中运行，该任务来自渲染任务源，而不是每轮事件循环必经的固定阶段。

继续追问时还可以讨论：计时器的最小延迟为什么不是执行时刻、多个任务源之间能否仅凭入队时间判断顺序，以及如何用 Performance 面板识别长任务和掉帧。
